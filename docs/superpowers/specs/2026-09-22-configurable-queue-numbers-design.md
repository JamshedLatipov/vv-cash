# Настраиваемый формат номера очереди

**Дата:** 2026-09-22
**Репозиторий:** `vv-cash`. Бэкенд (`cloudmarket-server`) не затрагивается.
**Статус:** реализовано, ветка feat/queue-number-format
**Ветка:** `feat/queue-number-format`, от `main`
**Продолжает:** `2026-08-31-order-queue-design.md` — раздел «Номера»

## Контекст

Очередь работает (см. спеку от 2026-08-31): касса выдаёт трёхзначный номер из
пула 100–999, пул перемешан по дню, каждой кассе — свой срез `n % 5 == TillIndex`,
номер печатается на талоне и бегунке, уезжает на KDS и табло.

Заказчик просит три вещи:

1. **Буква кассы** в номере: `A-123` на первой кассе, `B-45` на второй.
2. **Настраиваемый диапазон** чисел вместо жёстких 100–999: маленькой точке
   хватает 1–99.
3. **Выключаемое перемешивание**: часть точек хочет `1, 2, 3…` по порядку и
   готова к тому, что по двум талонам считается оборот.

Что сейчас мешает:

| Что | Где | Почему мешает |
|---|---|---|
| `Tills = 5` константа | `NumberPool.cs` | Одиночная касса получает 1/5 любого диапазона: при 1–99 это 20 номеров, по порядку — `1, 6, 11` |
| `FirstNumber`/`LastNumber` константы | там же | Диапазон не настроить |
| `QueueOrder.Number` — `int` насквозь | модель, хранилище, JSON, страницы, печать | Букве негде жить |
| Пул пересобирается только по ключу `Day` | `NumberPool.EnsureTodaysPoolAsync` | Любая настройка пула вступает в силу завтра |

## Решения и почему

### 1. Буква — свободный префикс, вводится на каждой кассе

Не галка «буквы вкл/выкл» с автоматическим `A, B, C` из `TillIndex`, а поле
`QueueNumberPrefix`, до трёх символов, любые буквы, включая кириллицу. Пусто —
буквы нет, всё как сегодня.

Префикс **прибавляется как есть**, разделитель не отдельная настройка: оператор
пишет `A-` и получает `A-123`, пишет `A` — получает `A123`. Одно поле вместо
двух, и никакой логики «а если разделитель, а если нет».

Уникальность буквы между кассами **не проверяется**: сервер очереди не знает
настроек касс, а кассы друг о друге — тем более. Та же договорённость, что уже
принята для `TillIndex`: две кассы с одинаковым индексом сегодня выдают
одинаковые номера, и это ответственность того, кто настраивает точку.

### 2. «Касс на точке» — настройка, а не константа

Рассматривались три способа делить диапазон:

- **A. Буква разводит кассы.** Префикс задан → касса берёт весь диапазон;
  пуст → срез `% 5`, как сейчас. Новых полей нет, но одиночная касса без буквы
  по-прежнему получает пятую часть диапазона.
- **B. `TillCount` — настройка.** Срез `% TillCount`. Одиночная касса ставит 1 и
  получает всё. Кассы с буквами тоже ставят 1: буква сама их разводит.
- **C. A и B вместе.** Два правила деления — труднее объяснить оператору.

Выбран **B**: один механизм, работает и одиночной кассе без буквы, и точке с
буквами, и точке без букв. Цена — ещё одно поле и строка в подсказке «с буквами
на каждой кассе ставьте 1».

`TillCount` по умолчанию 5 — ровно сегодняшняя константа, миграция нулевая.

### 3. Два правила среза: по остатку и блоками

При **включённом** перемешивании срез остаётся `(n − Min) % TillCount == TillIndex`.
При `Min = 100`, `TillCount = 5` это в точности сегодняшний `n % 5`
(`100 % 5 == 0`), так что действующие точки после обновления не замечают
ничего — даже если кассы обновятся в разное время одного дня, их срезы не
столкнутся.

При **выключенном** перемешивании срез — сплошные блоки, диапазон делится
поровну: каждая касса получает `count / TillCount` номеров, первые
`count % TillCount` касс — на один больше. Диапазон 1–99 на две кассы даёт
`1–50` первой и `51–99` второй, и номера идут `1, 2, 3…`, а не `1, 3, 5…`.

Не `ceil(count / TillCount)` с хвостом последней кассе: при `100–120` на
девять касс `ceil` даёт по три номера первым семи и **ничего** восьмой и
девятой, а предпросмотр в настройках показывает срез только своей кассы —
оператор кассы 0 такой конфигурации не увидел бы. Ровное деление гарантирует
каждой кассе хотя бы один номер, пока `count ≥ TillCount`.

Почему не блоки всегда: шаффл делает вид среза невидимым для клиента, а смена
`%`-среза на блочный посреди дня на точке, где кассы обновились не одновременно,
столкнула бы старую и новую кассы на один день. Незачем платить этот риск за
косметику, которую никто не видит.

### 4. Пул пересобирается по отпечатку настроек, не только по дню

Сегодня ключ пересборки — `Day`. Станет `PoolKey`:

```
{day}|{min}|{max}|{shuffle}|{tillCount}|{tillIndex}
```

Не совпал с сохранённым → `DELETE + INSERT` в одной транзакции, как при смене
дня. Значит любая из этих настроек применяется **на следующем талоне**, без
перезапуска и без ожидания завтра. Сегодняшняя оговорка «номер кассы вступает
в силу со следующего дня» уходит — вместе с текстом `QueueSettingsNotice`.

Оговорка, которая её заменяет: пересборка забывает, какие номера сейчас на
руках, поэтому менять эти поля — между сменами. То же, что и раньше было
сказано про `TillIndex`, только честнее: раньше отложенное на завтра
столкновение всё равно наступало, просто позже.

`QueueSecret` в ключ **не входит**: он влияет только на порядок перемешивания,
а порядок уже лежит в таблице. Новый секрет подхватится при следующей
пересборке, как и сегодня.

Следствие для `NumberPool`: настройки читаются **на каждой выдаче**, а не
один раз в конструкторе.

### 5. Число остаётся числом, буква едет рядом

`QueueOrder.Number` остаётся `int`. Добавляются `Prefix` (string, `""`) и
вычисляемый `Label => Prefix + Number` (invariant culture).

Отвергнуто одно строковое поле `"A-123"`: пул, `ReleaseAsync(int, Guid)` и три
SQL-запроса выбора номера работают с числом; менять тип колонки `Number` в
SQLite и переписывать сравнения ради оформления — риск без выигрыша.

### 6. Исчерпание пула: свободный номер раньше живого, кулдаун уходит

Правка, которую делает нужной именно настраиваемый диапазон — и которая по
ходу дела показала, что кулдаун в 50 выдач был мёртвым правилом.

Сегодня выбор номера идёт в три ветки: свежий; возвращённый и отстоявший
кулдаун (≥ 50 выдач с момента возврата); иначе — `ORDER BY
COALESCE(IssuedSeq, ReleasedAtSeq, 0)`, «номер с самым давним событием».
Третья ветка может предпочесть **живой** номер, выданный на seq 10,
**свободному**, возвращённому на seq 30: у второго клиента на руках отберут
талон, хотя рядом лежит ничей. Со 180 номерами на кассу ветка практически
недостижима; с диапазоном 1–30 это обычный обед: кулдаун никогда не
проходит, вторая ветка никогда не срабатывает, и в третью попадает каждая
выдача после тридцатой.

Правильный порядок предпочтений: **свежий → свободный (самый давно
возвращённый первым) → живой (самый давно выданный первым)**. Живой номер
отбирается только когда свободных нет вовсе — это ветка для точки без
кухонного экрана, где заказы никто не закрывает, и без неё касса встала бы
намертво.

Под этим порядком кулдаун теряет смысл, и это доказуемо: «отстоявшие» — это
подмножество свободных с наименьшими `ReleasedAtSeq`, так что «сначала
отстоявшие по `ReleasedAtSeq`, потом остальные свободные по `ReleasedAtSeq`»
даёт в точности тот же результат, что «все свободные по `ReleasedAtSeq`».
Кулдаун мог изменить исход только одним способом — заставив кассу отобрать
живой номер вместо недавно освобождённого, — и ровно это в нём и было
неправильно.

Что кулдаун обещал заказчику — «один и тот же номер не окажется у двух
человек одновременно» — новый порядок даёт сильнее, а не слабее: свободный
номер возвращается в оборот только после всех свежих и всех освобождённых
раньше него. На 180-номерной кассе с 10–30 живыми заказами это разрыв в
150+ выдач вместо 50; на крошечном диапазоне — максимум, который возможен
без дублирования живого номера. Для действующих точек поведение после
первого прохода по срезу не меняется: самый давно освобождённый номер и
раньше всегда оказывался отстоявшим.

Следствие: константа `CooldownIssues` и вторая ветка удаляются;
`ReleasedAtSeq` остаётся — по нему упорядочиваются свободные. Пять
существующих тестов, которые фиксировали ширину кулдауна через исчерпание
среза с одним освобождённым номером, на деле фиксировали «отбери 49 живых
номеров прежде чем вернуть свободный» — они переписываются под настоящие
инварианты (см. «Тесты»).

## Настройки

### `IQueueSettings` / `SettingsData`

| Поле | Тип | По умолчанию | Геттер `SettingsService` |
|---|---|---|---|
| `QueueNumberPrefix` | string | `""` | `Trim()`, обрезка до 3 символов, `null → ""` |
| `QueueNumberMin` | int | `100` | clamp 1..9999 |
| `QueueNumberMax` | int | `999` | clamp `Min`..9999 |
| `QueueNumberShuffle` | bool | `true` | — |
| `TillCount` | int | `5` | clamp 1..9 |
| `TillIndex` | int | `0` | clamp 0..`TillCount − 1` (сейчас 0..4) |

Нормализация в геттерах, как у `QueuePort` и `TillIndex` сегодня: `settings.json`
правят руками, и мусор в поле должен читаться как безопасное значение, а не
класть загрузку. Файл без новых полей = сегодняшнее поведение.

`Max ≥ Min` гарантируется геттером, но срез может оказаться пустым (`1–3`, пять
касс, `TillIndex = 4`). Это не чинится молча: `NumberPool.IssueAsync` бросает
`InvalidOperationException`, как сегодня, `QueueClient` гасит его и возвращает
`null`, талон не печатается. Ловится до сохранения строкой предпросмотра в
настройках (см. UI).

### Снимок для пула

Пулу нужны шесть значений разом и согласованно, а не шесть свойств, каждое из
которых могло измениться между чтениями. Поэтому:

```csharp
public sealed record QueueNumberOptions(
    int TillIndex, int TillCount, int Min, int Max, bool Shuffle,
    string Prefix, string Secret)
{
    public static QueueNumberOptions From(IQueueSettings s) => new(
        s.TillIndex, s.TillCount, s.QueueNumberMin, s.QueueNumberMax,
        s.QueueNumberShuffle, s.QueueNumberPrefix, s.QueueSecret);

    /// Сегодняшние константы — для тестов и для места, где IQueueSettings нет.
    public static QueueNumberOptions Default(int tillIndex, string secret) =>
        new(tillIndex, 5, 100, 999, true, "", secret);

    /// Истинно, когда пул на диске, собранный кодом до этой спеки (он знал
    /// только константы), совпал бы с пулом от этих настроек. См. «Пересборка».
    public bool ShapesTheLegacyPool => TillCount == 5 && Min == 100 && Max == 999 && Shuffle;
}
```

`NumberPool(QueueStorage, Func<QueueNumberOptions>, Func<DateTime>)` — снимок
берётся один раз в начале `IssueAsync`, под семафором, и от него считаются и
`PoolKey`, и срез. `Prefix` и `Secret` в `PoolKey` не входят. Семь вызовов
`new NumberPool(storage, 0, "secret", Now)` в тестах становятся
`new NumberPool(storage, () => QueueNumberOptions.Default(0, "secret"), Now)`.

`QueueClient` берёт тот же `Func<QueueNumberOptions>` и читает из снимка
`TillIndex` и `Prefix` **на каждом заказе** (тем же приёмом, что
`HttpQueueTransport` читает секрет), а не один раз в конструкторе: иначе пул
уже выдаёт номера нового индекса, а на заказе стоит старый.

## Пул

### Срез

```
count   = Max − Min + 1
shuffle:  { n ∈ [Min..Max] : (n − Min) % TillCount == TillIndex }
sequential:
  base  = count / TillCount,  rem = count % TillCount
  start = Min + TillIndex · base + min(TillIndex, rem)
  size  = base + (TillIndex < rem ? 1 : 0)
  [start .. start + size − 1]
```

### Порядок

Перемешивание — Фишер—Йетс на `QueueShuffleKeystream(day, tillIndex, secret)`,
без изменений. По порядку — `Position` совпадает с возрастанием `n`.

### Пересборка

`EnsureTodaysPoolAsync` → `EnsurePoolAsync(options)`: читает `QueueState['PoolKey']`,
сравнивает с вычисленным, при расхождении — `DELETE FROM NumberPool`, вставка
среза, `IssueSeq = 0`, запись `PoolKey`.

**Наследие ключа `Day`.** На действующей базе `PoolKey` нет, есть `Day`.
Пересобрать пул просто так нельзя: порядок детерминирован по дню, `IssueSeq`
обнулится, и касса заново выдаст те номера, что уже роздала с утра — прямо
в руки второму клиенту. Поэтому при отсутствующем `PoolKey`:

- `Day == сегодня` **и** `options.ShapesTheLegacyPool` → пул на диске и есть
  пул от этих настроек: записать `PoolKey`, таблицу не трогать;
- иначе → пересобрать, как при смене дня.

`Day` после этого не пишется и не читается. Ветка отмирает сама: на следующий
день `PoolKey` уже есть.

### Выбор номера

Три ветки вместо трёх прежних, но с другим смыслом — см. решение 6:

```sql
-- 1: нетронутый — по позиции в перемешанном (или возрастающем) порядке
SELECT Number FROM NumberPool
WHERE IssuedSeq IS NULL AND ReleasedAtSeq IS NULL
ORDER BY Position LIMIT 1;

-- 2: свободный — самый давно возвращённый
SELECT Number FROM NumberPool
WHERE IssuedSeq IS NULL AND ReleasedAtSeq IS NOT NULL
ORDER BY ReleasedAtSeq LIMIT 1;

-- 3: свободных нет вовсе — самый давно выданный
SELECT Number FROM NumberPool
ORDER BY IssuedSeq LIMIT 1;
```

Ветка 1 — без изменений. Прежняя ветка 2 (кулдаун) удалена вместе с
`CooldownIssues`. Прежняя ветка 3 (`COALESCE`) заменена на две.

## Путь буквы

```
IQueueSettings.QueueNumberPrefix
  └─ QueueClient.EnqueueAsync / IssueNumberAsync
       ├─ QueueOrder { Number, Prefix, Label }       → QueueStorage (колонка Prefix)
       │                                             → POST /orders → сервер → SQLite
       │                                             → GET /orders, WS → kds.html, board.html (o.label)
       └─ PosViewModel.ProceedToPayAsync: label
            ├─ IPrinterService.PrintTicketAsync(label, …)        уже string
            ├─ IPrinterService.PrintKitchenOrderAsync(sale, label) уже string
            └─ ReceiptRenderer ["queue"] = label                   уже string
```

**`IQueueClient.IssueNumberAsync`** (ветка `QueueRole = Off`, только печать)
возвращает `Task<int?>` → станет `Task<string?>` — готовый `label`. Заказа эта
ветка не создаёт и номер никогда не освобождает (см. её докстринг), так что
число как таковое никому за пределами пула не нужно. `PosViewModel` в обеих
ветках получает строку — `QueueOrder.Label` или результат `IssueNumberAsync` —
и больше не форматирует число сам.

**`QueueStorage`:** `ALTER TABLE QueueOrders ADD COLUMN Prefix TEXT` через
существующий `AddColumnIfMissingAsync`; чтение `IsDBNull → ""`. Строки,
записанные до обновления, — без буквы, как и были напечатаны.

**По проводу:** `JsonSerializerDefaults.Web` сериализует `prefix` и `label`
(get-only свойство сериализуется, при десериализации игнорируется). Страницы
`kds.html` и `board.html` рендерят `o.label` вместо `o.number`; подтверждение
отмены на KDS (`Отменить заказ № …`) — тоже `label`. Страницы отдаёт сам
сервер, версии совпадают, fallback на `o.number` не нужен.

Старый сервер + новый клиент: неизвестное поле `prefix` игнорируется,
табло показывает голое число — деградация, не поломка. Новый сервер + старый
клиент: `prefix` отсутствует → `""`.

**Печать:** `BuildTicket` печатает `label` двойной высотой и шириной; `A-1234`
— 6 символов, при 2× на 58-мм ленте (16 символов в строке) помещается с
запасом. Максимум по нормализации: 3 символа префикса + 4 цифры = 7.

## UI настроек

Блок «Очередь» в `SettingsView.axaml`. Новые поля видны **всегда**, как
`TillIndex`, — печать номера работает и при `QueueRole = Off`.

```
[Роль очереди ▾]  [Буква кассы]  [Касс на точке]  [Номер кассы]
[Номера от]       [до]           [☑ Перемешивать номера]
Предпросмотр: A-100 … A-999 — 180 номеров на эту кассу
```

- Числовые поля — строками (`…Text`), как `QueuePortText`/`TillIndexText`,
  разбор при сохранении.
- **Предпросмотр** считается в `SettingsViewModel` из введённых значений по
  тем же формулам среза: первый и последний номер среза с префиксом и их
  количество. Пустой срез → «Касса не получит ни одного номера» красным. Это
  единственное место, где опечатка в диапазоне видна до того, как талон не
  напечатался.
- `QueueSettingsNotice` → «Роль, порт и секрет применяются сразу после
  сохранения. Формат номера — на следующем талоне; менять его между сменами:
  пересборка пула забывает, какие номера сейчас на руках. Если у каждой кассы
  своя буква, ставьте «Касс на точке» = 1.»

i18n — пять файлов `Assets/i18n/{ru,en,uz,kk,tg}.json`, ключи:
`QueueNumberPrefix`, `TillCount`, `QueueNumberMin`, `QueueNumberMax`,
`QueueNumberShuffle`, `QueueNumberPreview`, `QueueNumberPreviewEmpty`,
обновлённый `QueueSettingsNotice`.

## Миграция

| Что | Было | Стало | На действующей кассе |
|---|---|---|---|
| `settings.json` | без новых полей | инициализаторы | 100–999, перемешано, 5 касс, без буквы — без изменений |
| `QueueState` | ключ `Day` | ключ `PoolKey` | первая выдача записывает `PoolKey`, пул на диске остаётся (см. «Наследие ключа `Day`») |
| `QueueOrders` | без `Prefix` | `ALTER TABLE … ADD COLUMN` | старые строки читаются как `""` |
| `NumberPool.Tills` | `internal const 5` | `TillCount` из настроек | `SettingsService.TillIndex` зажимает по `TillCount` |

Ни один шаг не требует действий на точке.

**`NumberPoolTest`**
- Настройки по умолчанию → срез тот же, что у прежней константы: для каждого
  `n ∈ 100..999` принадлежность кассе совпадает с `n % 5 == TillIndex`.
- Перемешивание выкл, 1–99, две кассы → касса 0 выдаёт `1, 2, 3 … 50` подряд,
  касса 1 начинает с `51`; ни один номер не в двух срезах.
- Перемешивание вкл, `Min = 7`, `Max = 63`, три кассы → срезы не пересекаются,
  объединение = весь диапазон.
- `TillCount = 1` → срез равен всему диапазону.
- Смена диапазона посреди дня → следующая выдача идёт из нового пула; те же
  настройки повторно → пул не тронут (перезапуск не сбивает выданное).
- Смена `TillIndex` посреди дня → пул пересобран (замена сегодняшнего
  «вступает в силу завтра»).
- База со старым ключом `Day == сегодня`, без `PoolKey`, три номера уже
  выданы, настройки по умолчанию → следующая выдача продолжает с четвёртого,
  `PoolKey` записан, `Day` не трогается. Те же условия, но `Max = 500` →
  пересборка.
- Исчерпание: срез из трёх номеров, все выданы, вернули второй → четвёртая
  выдача даёт именно его, а не первый (живой, выданный раньше).
- Исчерпание без единого свободного → самый давно выданный, как сейчас.
- Свободный номер возвращается только после всех свежих и всех освобождённых
  раньше него: из 180 выдано 100, освобождён первый → следующие 80 выдач —
  свежие, 181-я — он; освобождены A, затем B → возвращаются A, потом B.
- Повторный возврат того же заказа не двигает номер в очереди свободных
  (переписанный `ARepeatedReleaseDoesNotPushTheCooldownWindowOut`).
- Стале-возврат уже переизданного номера не освобождает его (переписанные
  `AStaleReleaseForAReissuedNumberDoesNotFreeALiveOrder` и, в
  `QueueClientTest`, `AStaleClosedOrderReplayDoesNotFreeANumberIssuedToSomeoneElse`,
  `RepeatedFlushesOfTheSameClosedOrderDoNotStallItsCooldown`): сценарий тот
  же, но переиздание наступает сразу после исчерпания свежих, а не через 50
  выдач.
- Пустой срез → `InvalidOperationException`.

**`QueueSettingsTest`**
- Файл `{}` → `100`, `999`, `true`, `5`, `""`.
- `Max < Min` → `Max == Min`; `Min = 0` → `1`; `Max = 99999` → `9999`.
- `TillCount = 0` → `1`; `TillCount = 50` → `9`.
- `TillIndex = 3` при `TillCount = 2` → `1`.
- Префикс `"  ABCD "` → `"ABC"`; `null` → `""`.

**`QueueClientTest`**
- `EnqueueAsync` проставляет `Prefix` из настроек, `Label == Prefix + Number`.
- `IssueNumberAsync` возвращает `Label` с префиксом.

**`QueueStorageTest`**
- `Prefix` переживает `SaveOrderAsync`/чтение; база, созданная без колонки,
  читает `""`.

**`QueueServerTest`**
- В JSON `GET /orders` у заказа есть `label`, равный `prefix + number`.

**`SettingsViewModelTest`**
- Предпросмотр для `A-`, 1–99, 2 кассы, индекс 1, без перемешивания →
  `A-51 … A-99 — 49 номеров`; для пустого среза — строка про «ни одного».

**`QueueServerStaticTest`** — если проверяет содержимое страниц, добавить
`o.label`; иначе не заводить.

## Что сознательно не делается

- **Ведущие нули** (`A-007`) — не выбрано заказчиком.
- **Буква от типа заказа или категории** — не просили; префикс — свойство
  кассы.
- **Проверка уникальности буквы или индекса между кассами** — сервер не знает
  настроек касс; договорённость та же, что для `TillIndex`.
- **Синхронизация настроек между кассами** — её нет и не было.
- **Кулдаун под размер среза** — кулдауна больше нет вовсе, см. решение 6.
- **Бэкенд не трогается.**
