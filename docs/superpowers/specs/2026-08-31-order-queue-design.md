# Очередь заказов и роли принтеров

**Дата:** 2026-08-31
**Репозиторий:** `vv-cash`. Бэкенд (`cloudmarket-server`) не затрагивается.
**Статус:** спека написана, ждёт ревью
**Ветка:** `feat/order-queue`, от `main`

## Контекст

Точке нужна производственная очередь: клиент оплачивает на кассе, получает талон
с номером, состав заказа уезжает на кухню, заказ живёт по состояниям, готовые
номера показываются на табло.

Парк неоднородный, и это главное ограничение проектирования:

- Кухня **иногда** с экраном, **иногда** только бумага.
- Табло в зале **у кого-то есть, у кого-то нет**.
- 1–5 касс на точке, локалка есть, интернет нестабилен.

Отсюда: экран кухни и табло — необязательные клиенты. Ядро обязано работать,
когда их нет вообще, и когда сеть отвалилась посреди дня.

### Что уже есть в коде

| Что | Где | Состояние |
|---|---|---|
| Фанаут печати | `Services/Hardware/CompositePrinterService.cs` | Шлёт чек на **все** включённые принтеры. Ролей нет |
| Конфиг принтера | `Models/PrinterConfig.cs` | `Name`, `ConnectionType`, `ConnectionString`, `IsEnabled`, `CodePageId` |
| Сборка чека | `Services/Hardware/EscPosPrinterService.cs` | Статические `BuildSaleReceipt`, `BuildPreReceipt`, `BuildReturnReceipt`, `BuildExchangeReceipt` |
| Локальное хранилище | `Services/Data/OfflineStorageService.cs` | SQLite, миграции через `InitializeCoreAsync` / `AddColumnIfMissingAsync` |
| Буфер недоставленного | там же | `SaveUnsyncedDocumentAsync` / `MarkDocumentRejectedAsync` — готовый образец для очереди |
| Настройки | `Services/SettingsService.cs` | `settings.json`, правится руками (так и написано в комментарии) |
| Палитра | `Assets/Styles/Colors.axaml` | Единственный источник цветов приложения |

Техбаза: `net10.0`, self-contained publish (`includedFrameworks` в
`VvCash.runtimeconfig.json`), Avalonia 11.2.3, `Microsoft.Data.Sqlite`, xunit.

## Решения и почему

### 1. Мини-сервер на кассе, а не на бэкенде

Рассматривались три топологии: сервер на кассе, очередь на бэкенде, гибрид
(бэкенд как правда + локалка как запасной транспорт). Выбран **сервер на кассе**.

Причина отказа от бэкенда: интернет на точках плавает, а кухонный экран и табло
без источника правды слепнут ровно в тот момент, когда точка работает.

Известная цена решения, принятая сознательно: главная касса — единая точка
отказа для *экранов*. Смягчается тем, что она **не** является точкой отказа для
*продаж* (см. решение 2).

### 2. Номер выдаёт та касса, которая пробила заказ

Это стержневое решение, из которого растёт всё остальное. Сервер — только
хранилище и раздатчик. Касса никогда ни у кого не спрашивает разрешения, чтобы
напечатать.

Следствие: сервер лежит → номер всё равно выдан, талон и бегунок напечатаны,
заказ лёг в локальный буфер и дошлётся позже. Кассир простоя не видит. Это
совпадает с тем, как уже устроены оффлайн-продажи, и не требует ни выборов
лидера, ни консенсуса, ни сведения расходящихся состояний.

Отвергнут вариант «любая касса подхватывает роль сервера, если главной нет N
секунд»: это выборы лидера со всеми их последствиями — расщепление мозга,
слияние состояний при возврате главной. Цена несоразмерна выигрышу.

### 3. Номера не должны выдавать оборот

Требование заказчика: по двум талонам нельзя посчитать, сколько чеков пробито за
день. Любой последовательный счётчик — включая счётчик с префиксом кассы — этому
не удовлетворяет: два номера вычитаются.

Решение: **пул перемешанных номеров**, каждой кассе — свой непересекающийся
класс вычетов.

Внутри, в базе, у заказа остаётся обычный идентификатор и связь с документом
продажи. Прячется только то, что видит клиент; прослеживаемость для учёта не
страдает.

Оговорка: у продажи, пробитой без интернета, номера документа ещё нет — это уже
описано в `IPrinterService` для чека. Заказ очереди связывается с продажей по
своему GUID, а `SaleDocumentNumber` проставляется, когда продажа доедет до
бэкенда. До этого момента поле пустое, и ни печать, ни экраны от него не зависят.

### 4. Клиенты кухни и табло — веб-страницы

KDS и табло — страницы, которые отдаёт сама касса-сервер. Клиентом становится
что угодно с браузером: Android-приставка к телевизору, планшет, второй монитор
кассы. Ставить и обновлять нечего.

Отвергнуто отдельное Avalonia-приложение: свой инсталлятор, свой автоапдейт,
только Windows — при том что оффлайн-кеш этим экранам не нужен, они бесполезны
без сервера по определению.

## Архитектура

```
Касса-сервер (QueueRole = Server)
  Kestrel :8770
    GET  /kds            → страница кухни
    GET  /board          → табло
    GET  /orders         → полный снимок (для переподключения)
    POST /orders         ← кассы-клиенты, идемпотентно по GUID
    POST /orders/{id}/state ← KDS
    WS   /ws             → пуш изменений всем подписчикам
  SQLite: queue_orders (заказы всей точки)
          queue_number_pool (свой пул этой кассы)

Касса-клиент (QueueRole = Client)
  SQLite: queue_number_pool (свой пул)
          queue_outbox (недоставленные заказы и переходы)

Касса без очереди (QueueRole = Off)
  Порт не открывается. Работает только печать.
```

`QueueRole = Off` — режим по умолчанию и основной режим для точек без экранов.
Печать номера, талона и бегунка при этом работает: очередь как *сетевая система*
и очередь как *набор документов* независимы.

### Аутентификация в локалке

Порт открыт всем в Wi-Fi точки. Общий секрет `QueueSecret` из настроек: кассы
шлют в заголовке, веб-страницы получают один раз в URL и кладут в `localStorage`.
Не криптография, а отсечение случайного гостевого планшета. Правило файрвола
прописывает инсталлятор.

### Новые файлы

```
Models/QueueOrder.cs            заказ: Id, Number, TillIndex, State, CreatedAt,
                                ReadyAt, ClosedAt, SaleDocumentNumber, Lines
Models/QueueOrderState.cs       New | InProgress | Ready | Closed | Cancelled
```

Publish self-contained, значит рантайм ASP.NET Core уезжает внутрь сборки: около
+12 МБ, автоапдейт донесёт.

## Номера

**Пул:** 100–999, девятьсот номеров, три цифры без ведущего нуля.

**Слайс кассы:** `number % 5 == TillIndex`, по 180 номеров на кассу. Пересечений
нет по построению — договариваться не о чем, поэтому оффлайн бесплатен.
`TillIndex` (0–4) — новая настройка.

**Перемешивание:** Fisher–Yates, сид = хеш от `дата + TillIndex + QueueSecret`.
Порядок пишется в `queue_number_pool` и живёт день. Наблюдатель с двумя талонами
вычитанием не получает ничего.

**Переиспользование:** номер возвращается в пул, когда заказ закрыт, но не
выдаётся снова, пока после него не ушло ещё 50 номеров. Без этой отсрочки на
руках у двух человек одновременно окажется один и тот же «305».

**Исчерпание:** если свободных нет вовсе — берётся освобождённый раньше всех.
180 номеров с оборотом покрывают любой реальный день; ветка существует, чтобы
касса не встала.

**Смена дня:** при первой продаже нового дня пул перемешивается заново, а
незакрытые вчерашние заказы закрываются автоматически — иначе их номера заняты
навсегда.

**Расхождение часов между кассами** значения не имеет: пулы независимы, день у
каждой кассы свой.

## Печать

### Роли

```csharp
[Flags]
public enum PrintRole { None = 0, Receipt = 1, Ticket = 2, KitchenOrder = 4 }
```

В `PrinterConfig` — `public PrintRole Roles { get; set; } = PrintRole.Receipt;`

Инициализатор и есть миграция: у существующих касс поля в `settings.json` нет,
`System.Text.Json` оставляет значение инициализатора, поведение не меняется. Тот
же приём, что уже применён для `CodePageId`.

Сериализация строкой (`JsonStringEnumConverter`): `settings.json` правят руками,
`"Receipt, Ticket"` там читается, а `3` — нет.

В настройках у каждого принтера три галки. Ни у одного принтера нет `Ticket` →
талон не печатается; это не ошибка, а конфигурация точки.

### Документы

| Документ | Содержимое | Кому |
|---|---|---|
| Чек | Как сейчас. **Без** номера очереди | Клиенту |
| Талон | Номер двойной высотой и шириной (`GS !`), под ним время и название точки | Клиенту, отдельной бумажкой |
| Бегунок | Тот же рендер чека, с ценами, плюс номер в шапке | На кухню |

Бегунок и чек собирает **одна** функция: у существующей
`EscPosPrinterService.BuildSaleReceipt` появляется параметр `string? queueNumber`
— пусто для чека, номер в шапку для бегунка. Отдельной логики для повара нет.
Талон — своя небольшая `BuildTicket`.

`IPrinterService` прирастает `PrintTicketAsync` и `PrintKitchenOrderAsync`.
`CompositePrinterService` вместо «шлём на все включённые» фильтрует список по
флагу — три подмножества одного списка. Порядок: чек, талон, бегунок.

### Изоляция отказов

Сейчас метод возвращает один общий `bool`. Станет три независимых результата:
кухонный принтер сдох — чек всё равно напечатан, продажа закрыта, кассир видит
предупреждение, а заказ в очереди есть и на KDS появится. Терять продажу из-за
кухонной железки нельзя.

Печать чека вызывается из двух мест, но очередь касается только одного:
`ProceedToPayAsync` (`ViewModels/PosViewModel.cs:2318`) — завершение продажи.
Кнопка «Печать чека» (`PrintReceipt`, `:1822`) остаётся нетронутой: она печатает
копию уже пробитого чека, и выдавать на неё новый номер значило бы плодить
заказы на кухне при каждом повторе.

## Веб-клиенты

Статика вшита в сборку как `EmbeddedResource`, не лежит файлами рядом — иначе
автоапдейт разъедется с кодом. Один HTML на страницу, ванильный JS, **никакого
npm в .NET-репозитории**.

### Оформление

Страницы должны выглядеть как продолжение кассы, а не как чужая админка.
Источник правды по цветам — `Assets/Styles/Colors.axaml`; `theme.css` повторяет
его как CSS-переменные:

| Токен | Значение | Роль |
|---|---|---|
| `--primary` | `#0075e2` | Акцент, активное состояние |
| `--primary-dark` | `#0063c7` | Нажатие |
| `--primary-light` | `#e6f1fc` | Подложка акцента |
| `--background` | `#f6f8f8` | Фон страницы |
| `--card` | `#ffffff` | Карточка заказа |
| `--text-primary` | `#0f172a` | Номер, названия |
| `--text-secondary` | `#64748b` | Подписи |
| `--text-muted` | `#94a3b8` | Время, служебное |
| `--success` | `#22c55e` | Готов |
| `--danger` | `#ef4444` | Отмена |
| `--border` | `#e2e8f0` | Границы карточек |

Шрифт — Inter, тот же, что в приложении (`Avalonia.Fonts.Inter`), вшит в статику,
не тянется из сети: на точке может не быть интернета. Радиусы — 8 / 12 / 16, как
в `Controls.axaml`. Светлая тема, как и всё приложение.

Расхождение палитры ловится тестом: он разбирает `Colors.axaml` и `theme.css` и
падает, если значение токена в них разошлось. Иначе первый же правленый цвет в
приложении молча оставит экраны в старом.

### KDS (`/kds`)

Карточки заказов, тап по карточке двигает состояние вперёд. Кнопки крупные —
кухня, руки мокрые, перчатки. Отмена — длинным нажатием, чтобы не смахнуть заказ
рукавом.

### Табло (`/board`)

Два столбца — «Готовятся» и «Готовы». Номер крупно, размер подгоняется под
количество заказов. Новый «готов» подсвечивается на несколько секунд.

### Транспорт

WebSocket `/ws`, сервер пушит изменения. Обязательная деталь: при обрыве —
переподключение с нарастающей паузой и **полный перезапрос** `/orders` при
возврате связи. Без этого табло тихо замирает со старыми номерами и никто не
замечает — самая частая поломка таких экранов.

## Деградация

| Событие | Поведение |
|---|---|
| Касса-клиент не достучалась до сервера | Номер выдан, бумага вышла, заказ в `queue_outbox`, повторная попытка раз в 15 секунд — сосед по локалке возвращается за секунды, а не за минуты. Свой значок в интерфейсе, отдельный от неотправленных документов: чинятся они по-разному |
| Сервер вернулся | Буфер досылается. `POST /orders` идемпотентен по GUID — повтор не создаёт дубль |
| Касса-сервер перезагрузилась | Заказы в её SQLite, поднялась — состояние на месте. Экраны переподключились сами |
| KDS отвалился | Заказы копятся, повар работает по бумаге. Вернулся — увидел всё |
| Порт 8770 занят | Сервер не поднялся, **касса работает дальше**, в настройках красная строка. Падать нельзя |
| Смена дня | Пул перемешивается, вчерашние незакрытые заказы закрываются автоматически |

## Миграция

`QueueRole` по умолчанию `Off`, `Roles` по умолчанию `Receipt`. На действующей
кассе после обновления не меняется ничего: порт не открывается, экраны не
появляются, чек печатается как печатался. Новые таблицы заводятся через
существующий путь `InitializeCoreAsync` / `AddColumnIfMissingAsync`.

## Тесты

xunit, `tests/VvCash.Tests`.

**`NumberPool`**
- Дубликатов не выдаёт.
- Номер возвращается в оборот только после 50 других.
- Пул исчерпан → берётся освобождённый раньше всех.
- Смена дня перемешивает заново.
- Слайсы двух касс не пересекаются.
- Порядок выдачи не монотонен — тот самый анти-подсчёт: подряд идущие выдачи не
  идут подряд по значению.

**`CompositePrinterService`**
- Три принтера с разными флагами → каждый получил ровно свой документ.
- Кухонный принтер упал → результат чека остался `true`.

**Миграция настроек**
- `settings.json` без `Roles` читается как `Receipt`.

**`QueueClient`**
- Сервер лежит → номер выдан, печать вызвана, заказ в буфере.
- Сервер вернулся → досыл.
- Двойная отправка → один заказ.

**`QueueServer`**
- Допустимые переходы состояний проходят, недопустимые отклоняются.

**Оформление**
- Токены `Colors.axaml` и `theme.css` совпадают.

Известная особенность репозитория: полный прогон иногда роняет случайный тест
через гонку Avalonia Dispatcher. Упал тест не по теме — смотреть стек, а не диф.

## Что сознательно не делается

- **Бэкенд не трогается.** Ни эндпоинтов, ни миграций по тенантам, ни новой
  авторизации. Заказ связан с документом продажи, а тот уезжает на бэкенд своим
  путём, так что аналитика по продажам не теряется. Теряются тайминги кухни —
  их стоит добавлять, когда очередь уже работает и понятно, какие именно нужны.
- **Выборы лидера и подхват роли сервера.** См. решение 2.
- **Локальный запасной транспорт для экранов** (поиск касс по mDNS, когда сервер
  недоступен). Обсуждался как этап 2 гибридной топологии; отложен.
- **Модификаторы и комментарии к позициям.** Бегунок печатает состав чека как
  есть.
