# Настраиваемый чек продажи (конструктор блоков)

**Дата:** 2026-09-01
**Репозитории:** `vv-cash` (касса), `cloudmarket-server` (бэкенд), `bozor` (бэкофис)
**Статус:** касса реализована; сервер и бэкофис — отдельными планами
**Ветка:** `feat/configurable-receipt-template`

## Контекст

Раскладка чека продажи зашита в код целиком —
[`EscPosPrinterService.BuildSaleReceipt`](../../../src/VvCash/Services/Hardware/EscPosPrinterService.cs).
Зашито:

| Что | Где |
|---|---|
| Шапка `VV CASH POS` | строковый литерал |
| Подвал `Thank you for shopping!` | строковый литерал |
| Подписи `Doc #`, `Whse:`, `Seller:`, `Subtotal:`, `Discount:`, `TOTAL:` | литералы по-английски, мимо `I18nService` |
| Ширина ленты `32` | число в восьми местах |
| Порядок строк, разделители `----`, что печатать | поток управления метода |
| Логотип, QR, штрихкод | отсутствуют как класс |

Настраиваемо на сегодня только подключение принтера, кодовая страница и роли
([`PrinterConfig`](../../../src/VvCash/Models/PrinterConfig.cs)) — то есть *как* печатать,
но не *что*.

Магазины просят своё название, свой подвал, свои реквизиты и QR с номером документа.
Сейчас каждая такая просьба — правка кода и релиз кассы.

### Что уже есть на бэкенде (и чего это стоит)

Механизм конфигурации кассы существует с 2018 года и до сих пор не задействован под чек:

- таблицы `config_groups` / `config_options` / `configs` (значение на пару касса+опция);
- `GET /cashes/config/get/` — касса читает свой конфиг под своим токеном;
- `GET /cash/config/get/:cash/`, `PUT /cash/config/`, `POST /cash/config/option/` —
  бэкофис читает и правит под site-пермишенами (`permcode.CashGetConfig`,
  `permcode.CashConfigUpdate`);
- в bozor уже есть диалог `src/app/dialogs/cash/cash-settings/cash-settings.component.ts`,
  который рендерит опции по `value_type` и **неизвестный тип показывает как строку**,
  а не прячет.

Главное: **опция `receiptTemplate` в базе уже засеяна** миграцией
`20190728012331_fixture_for_cash_configs.up.sql` с описанием «Template for the receipt».
Читателей у неё нет ни одного — ни в Go, ни в кассе. Рядом лежат такие же мёртвые
`storeName`, `receiptPrinterPaperWidth`, `receiptPrinters`, `labelPrinters`, `lcdCOM`.

Следствие: заводить опцию не надо, нужна только миграция, дающая существующей строке
`code` и `value_type`.

**Риск отсюда:** у существующих тенантов в `configs.val` для `receiptTemplate` может
лежать произвольный мусор — диалог bozor рендерит её текстовым полем, и туда могли
что-то напечатать за шесть лет. Непарсящееся значение обязано читаться кассой как
«шаблона нет», а не как ошибка.

## Решения, принятые до начала

| Вопрос | Решение |
|---|---|
| Уровень настраиваемости | Конструктор блоков (не плоские галочки, не текстовый шаблон с циклами) |
| Источник конфига | Сервер; касса синхронизирует, как товары и категории |
| Где редактируется | Бэкофис bozor |
| Охват документов | **Только чек продажи.** Пречек, возврат, обмен, талон — остаются зашитыми |
| Набор блоков | База + QR/штрихкод + графический логотип + свободный текст с подстановками + настройка строки товара |
| Превью | Есть, в bozor |
| Мёртвые опции 2019 года | Не трогать. Ширина и название магазина живут внутри шаблона |

## Архитектура

### Слои на кассе

```
ReceiptTemplate (JSON с сервера)  +  SaleReceiptData (данные продажи)
                    │
                    ▼
        ReceiptRenderer.Render()        ← чистая функция: ни байтов, ни сокетов
                    │
                    ▼
          IReadOnlyList<ReceiptOp>      ← Text / Align / Bold / DoubleSize /
                    │                      Qr / Barcode / Image / Feed / Cut
                    ▼
         EscPosEmitter.Emit(ops, cp)    ← единственное место, знающее ESC/POS
                    │
                    ▼
                  byte[]
```

Два слоя вместо одного стоят примерно день работы и покупают три вещи:

1. раскладка тестируется как текст, а не как байты (нынешний `EscPosUnitTest` сравнивает байты);
2. ширина ленты становится параметром одного слоя, а не восемью литералами `32`;
3. превью в bozor рисуется из той же модели операций, а не из отдельного представления.

Рассмотренная и отклонённая альтернатива: **рендерить чек на сервере и слать на кассу
готовым**. Отпадает, потому что касса печатает офлайн — очередь продаж в
`OfflineStorageService` существует именно для разрыва связи, а без сети сервер раскладку
не отдаст.

### Модель шаблона

Новый namespace `VvCash.Models.Receipt`.

```csharp
public sealed class ReceiptTemplate
{
    public int Version { get; set; } = 1;   // для будущих несовместимых правок формата
    public int Width { get; set; } = 32;    // колонок ленты: 32 / 42 / 48
    public List<ReceiptBlock> Blocks { get; set; } = new();

    /// Ровно нынешняя раскладка. Касса, до которой шаблон не доехал, печатает
    /// то же, что печатала вчера — то же решение, что у CashFeatures.Default.
    public static ReceiptTemplate Default { get; }
}
```

Блоки — полиморфный JSON через `[JsonPolymorphic]` по полю `type` (штатно в net10).
У каждого блока есть `enabled: bool`; порядок задаётся позицией в списке.

| `type` | Настройки блока |
|---|---|
| `logo` | источник (`nv` со слотом принтера или `bitmap` из опции `receipt_logo`), выравнивание |
| `text` | строка с подстановками, выравнивание, жирность, двойной размер |
| `fields` | какие реквизиты и в каком порядке (номер документа, дата, склад, продавец, номер очереди), своя подпись у каждого |
| `items` | цена за единицу, артикул, штрихкод, вторая единица, скидка по строке; одна строка или две |
| `totals` | подытог / скидка / название скидки / ИТОГО; свои подписи; жирность |
| `qr` | данные с подстановками, размер модуля |
| `barcode` | данные, символика (Code128 / EAN13), высота, подпись под кодом |
| `line` | разделитель, символ настраивается |
| `feed` | сколько пустых строк |

**Подстановки** — плоские имена, без циклов и условий: `{doc}`, `{date}`, `{warehouse}`,
`{seller}`, `{subtotal}`, `{discount}`, `{total}`, `{queue}`. Цикл по товарам делает блок
`items`, а не язык шаблона — это сознательная граница, чтобы не заводить парсер.

Неизвестное имя подстановки печатается **как есть**. `{tota}` на бумаге сразу показывает,
где опечатка в бэкофисе; молча съеденная строка не показывает ничего.

### Синхронизация и кэш на кассе

Копия того, как устроены фичефлаги, включая причины:

- `SyncService.SyncReceiptTemplateAsync` дёргает `GET /cashes/config/get/`, находит опцию
  по `code`, кладёт сырое значение в SQLite-таблицу `Settings` под ключами
  `ReceiptTemplate` и `ReceiptLogo`;
- ошибка HTTP или `status != 0` → **остаётся закэшированное**. Потеря эндпоинта не должна
  откатывать магазин на дефолтный чек;
- значение не парсится → `ReceiptTemplate.Default` плюс запись в лог. Битый кэш не имеет
  права мешать кассе открыться — то же правило, что в `GetCashFeaturesAsync`;
- поверх — `IReceiptTemplateService` с `Current` и `RefreshAsync()`, устроенный как
  `ICashFeatureService`.

### Логотип

Растр готовит **bozor**, не касса: браузер грузит PNG на canvas, дизерит в 1 бит
(Floyd–Steinberg), масштабирует под ширину головки и сохраняет готовый битмап в base64.
Касса печатает его как есть через `GS v 0`.

Два следствия, ради которых так и сделано: в vv-cash не появляется библиотеки работы с
изображениями, и превью в бэкофисе показывает ровно те пиксели, что выйдут на бумагу.

Логотип живёт в **отдельной** опции `receipt_logo`, а не полем внутри шаблона: 7–8 КБ
base64 не должны ездить в каждом ответе конфига и висеть в редакторе блоков. Блок `logo`
только ссылается на источник и поддерживает второй режим — `nv` со слотом (`FS p`), для
точек, где логотип уже прошит в память принтера.

### Бэкенд

Одна миграция:

- существующей строке `config_options` с `name = 'receiptTemplate'` проставить
  `code = 'receipt_template'` и `value_type = 'json'`;
- завести опцию `receipt_logo` (готовой нет) с `value_type = 'json'`;
- расширить CHECK-ограничение `config_options_value_type_check` — сейчас там
  `('bool','number','string','enum')`. Postgres не умеет `ADD CONSTRAINT IF NOT EXISTS`,
  поэтому drop-then-add, как в `20260728000800_cash_feature_flags.up.sql`.

`validateConfigValue` (`cashes/config_models.go:146` в `cloudmarket-server`)
получает ветку `json`: значение разбирается, `version` знаком, все `type` блоков из
известного списка. Отказ — `errors.Coded` с конкретной причиной, то есть 400 через
`response.ServiceError`, как у существующих типов.

Известный список `type` на сервере и терпимость кассы к незнакомому `type` — не
противоречие, а разные стороны: сервер не даёт записать опечатку сегодня, касса переживает
блок из более новой админки, чем её собственная сборка.

**Поля внутри блоков сервер не проверяет.** Схема блоков и так живёт в двух местах (C# и
TS); полная копия ещё и в Go — гарантированный источник расхождений. Незнакомые поля
касса игнорирует.

### Бэкофис

`widgetFor` в `cash-settings.component.ts` получает ветку `json` → кнопка «Настроить»,
открывающая конструктор:

- список блоков на `cdkDropList` (`@angular/cdk` уже в зависимостях, Angular 20);
- панель свойств выбранного блока справа;
- ASCII-превью чека слева, перерисовывается на каждое изменение.

Старая сборка админки, не знающая типа `json`, покажет опцию текстовым полем —
`widgetFor` уже так устроен намеренно. Это деградация, а не поломка.

## Расхождение двух рендереров

Превью — вторая реализация раскладки, на TypeScript, ~200 строк. Иначе картинку не
получить: сервер JSON ни во что не превращает, а касса из браузера недоступна.

Отсюда риск: поправили расчёт отступа на C#, забыли в TS — превью показывает одно,
принтер выдаёт другое. Это хуже отсутствия превью: админ уверен, что видел результат.

**Принятая мера (дешёвая, полдня):**

- файл-эталон `receipt-golden.json` — шаблон + демо-продажа + ожидаемые строки чека;
- канонический экземпляр в `vv-cash`, копия в `bozor` кладётся скриптом;
- в файле поле `rendererVersion`; TS-рендерер объявляет версию, которую реализует;
  несовпадение валит тест bozor.

**Остаточная дыра, названная прямо:** если правится C#-рендерер, а копия эталона в bozor
не обновлена и `rendererVersion` не поднят — не упадёт ничего. Полностью это чинится
только монорепой, опубликованным пакетом или CI, который чекаутит оба репозитория.
Здесь сознательно взят паллиатив; если расхождения начнут случаться на практике, следующий
шаг — задача в CI bozor, тянущая эталон из vv-cash.

## Тесты

| Уровень | Что проверяет |
|---|---|
| Замок совместимости | Байты нынешнего чека снимаются как golden **до** правки; `ReceiptTemplate.Default` через новый путь обязан дать их байт-в-байт. Пока тест зелёный, обновление кассы без шаблона с сервера ничего на точке не меняет |
| `ReceiptRenderer` | Раскладка как текст: ширина 32/42/48, обрезка длинных названий, скрытые блоки, пустые реквизиты, неизвестная подстановка печатается как есть |
| `EscPosEmitter` | Операция → байты: выравнивание, жирность, двойной размер, `GS v 0`, `GS ( k`, `GS k`, `FS p` |
| Разбор шаблона | Битый JSON → `Default`; неизвестный `type` блока пропускается, остальные печатаются; незнакомое поле игнорируется |
| Синхронизация | HTTP-ошибка оставляет кэш; `status != 0` оставляет кэш; корректный ответ обновляет |
| Go | `validateConfigValue` для `json`: валидный, битый, неизвестный `type`, чужая `version` |
| bozor | Конструктор: перетаскивание, включение/выключение, свойства; превью против эталона; проверка `rendererVersion` |

## Оценка

| Репозиторий | Работа | Дни |
|---|---|---|
| `vv-cash` | Модель, рендерер, эмиттер, golden-замок, синхронизация, кэш, сервис | 3–4 |
| `cloudmarket-server` | Миграция, валидация `json`, тесты | 1 |
| `bozor` | Конструктор блоков, дизеринг логотипа, ASCII-превью | 3–4 |
| Общее | Эталон и скрипт копирования | 0.5 |

Итого 8–10 дней.

**Отдельной строкой:** миграцию надо прогнать по каждому тенанту — в cloudmarket одна база
на магазин, и мердж в основную ветку миграции не применяет.

## Что сознательно не делается

- Пречек, возврат, обмен, талон, бегунок — раскладка остаётся в коде. Внешне разойдутся с
  чеком продажи; это принято.
- Условия и циклы в шаблоне. Цикл по товарам — блок `items`, и только он.
- Локализация подписей средствами `I18nService`. Подписи задаёт магазин текстом в шаблоне;
  зашитые английские литералы уходят вместе с зашитой раскладкой.
- Оживление мёртвых опций `storeName` и `receiptPrinterPaperWidth`. Название магазина и
  ширина ленты живут внутри шаблона, один источник истины.
- Рендеринг чека на сервере. Касса печатает офлайн.
