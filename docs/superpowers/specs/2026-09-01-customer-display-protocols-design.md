# Протокол дисплея покупателя задаётся в настройках, с автоподбором

**Дата:** 2026-09-01
**Репозиторий:** `vv-cash` (клиент)
**Статус:** дизайн утверждён, ждёт ревью спеки

## Контекст и проблема

Касса умеет ровно один диалект дисплея покупателя. `VfdDisplayService` шлёт
`ESC @`, затем `ESC t n`, затем 40 символов двумя строками по 20 —
[`VfdDisplayService.cs`](../../../src/VvCash/Services/Hardware/VfdDisplayService.cs).
Это набор команд Epson/ESC-POS для текстового VFD 2×20, и в комментарии класса он
назван прямо.

В природе на кассах стоят не только такие табло. Распространены как минимум:

- **CD5220** — строка задаётся `ESC Q A` / `ESC Q B` и закрывается `CR`;
- **сегментные LED** — только цифры, 6–8 разрядов, букв не умеют физически;
- табло, принимающие **голый текст** без единой команды.

Табло, переключённое в чужой набор команд, наши байты не понимает. Текст не
появляется **ни на какой скорости**, а панель показывает своё заводское
состояние — на разборе это выглядело как «висит `00.0` и не меняется».

Отдельно от протокола есть транспорт. Порт открывается голым конструктором
`new SerialPort(portName, baudRate)`, то есть 8N1 и `DtrEnable = RtsEnable =
false`. Часть табло требует 7E1, часть не принимает данные без поднятых DTR/RTS,
а некоторые от этих линий ещё и питаются.

Наконец, подбор вслепую сегодня стоит нажатия на «Проверить дисплей» за каждую
комбинацию, а комбинаций десятки.

**Цель:** протокол и параметры кадра выбираются на экране настроек, а рабочая
комбинация ищется автоподбором, а не перебором вручную.

## Решение

Протокол становится записью каталога, как кодовая страница и формат телефона.
Транспорт остаётся один. На экране настроек появляется кнопка «Подобрать»,
которая гоняет комбинации «протокол × скорость» и на каждой шлёт на табло **её
номер цифрами** — цифры покажет и текстовое табло, и сегментное. Кассир видит
читаемое число, вводит его и жмёт «Применить».

Судьёй остаётся человек. Касса определить успех не может и притворяться не
будет: запись в порт удаётся и на неверной скорости — драйвер отдаёт байты, а что
с ними сделала панель, обратной связи нет, ESC/POS-табло не отвечает ничего.
Именно поэтому пробник — номер на табло, а не проверка кода возврата.

## Архитектура

### Протокол как сборщик кадра

Новый `src/VvCash/Services/Hardware/IDisplayProtocol.cs`. Протокол умеет только
превращать смысл в байты и ничего не знает о портах:

```csharp
public interface IDisplayProtocol
{
    string Id { get; }
    string DisplayName { get; }

    byte[] BuildLine(string line1, string line2, EscPosCodePage codePage);
    byte[] BuildItem(string name, decimal total, EscPosCodePage codePage);
    byte[] BuildTotal(decimal total, EscPosCodePage codePage);
    byte[] BuildClear(EscPosCodePage codePage);

    /// Кадр автоподбора: номер комбинации и ничего больше.
    byte[] BuildProbe(int number);
}
```

`BuildProbe` — отдельный метод, а не `BuildTotal(number)`. Через сумму номер
пришёл бы на табло как `7.00`, и кассиру пришлось бы догадываться, что вводить.
Кодовая страница ему не нужна: цифры одинаковы во всех однобайтовых таблицах, а
пробник обязан читаться в том числе тогда, когда таблица выбрана неверно — иначе
он проверял бы заодно и её.

Четыре реализации:

| Id | Что шлёт |
|---|---|
| `ESCPOS` | `ESC @`, `ESC t n`, 40 символов — нынешнее поведение, байт в байт |
| `CD5220` | `ESC Q A <строка1> CR`, затем `ESC Q B <строка2> CR` |
| `NUMERIC` | Только цифры суммы и `CR`, без единой команды |
| `RAW` | 40 символов, без команд |

`ESCPOS` обязан остаться побайтово тем, что уходит сегодня: это единственная
реализация, про которую известно, что она работает на живом железе в точках.
Тест сравнивает её выход с зафиксированными байтами, а не с «тем, что вернёт
код».

Сегментное табло встаёт сюда без единой ветки снаружи. `NUMERIC.BuildItem`
отбрасывает название и рисует сумму — решение «на цифровом всегда виден итог»
живёт внутри протокола, и `PosViewModel` о существовании цифровых табло не
узнаёт.

### Каталог

`DisplayProtocols` по образцу
[`EscPosCodePages`](../../../src/VvCash/Models/EscPosCodePage.cs): статические
поля на каждую запись, `All`, `Default` и единственное место, где `Id`
превращается в запись:

```csharp
public static IDisplayProtocol Default => EscPos;
public static IDisplayProtocol Resolve(string? id);   // пусто или незнакомое -> Default
```

`Default = ESCPOS` и откат незнакомого id туда же — то, что делает обновление
пустым для уже настроенных касс: в их `settings.json` нового ключа нет, `Resolve`
вернёт нынешнее поведение.

### Формат кадра

`SerialFramings` — каталог из двух записей, той же формы:

| Id | Данных | Чётность | Стоп |
|---|---|---|---|
| `8N1` | 8 | None | One |
| `7E1` | 7 | Even | One |

`Default = 8N1`, то есть опять же нынешнее поведение.

### Транспорт

`VfdDisplayService` сохраняет всё, что в нём есть сейчас, и это осознанно:
FIFO-очередь на `_tail`, `WriteTimeout`, и `catch`, который держит хвост в
`RanToCompletion` и не даёт упавшей отправке подвесить очередь для всех. Эта
логика тонкая и остаётся в одном экземпляре.

Конструктор дополняется протоколом, форматом кадра и признаком DTR/RTS. Методы
`ShowLineAsync`/`ShowItemAsync`/`ShowTotalAsync`/`ClearAsync` перестают собирать
байты сами и делегируют протоколу; `SendAsync` начинает принимать `byte[]`, а не
`string`.

Статические `BuildFrame`/`BuildItemFrame`/`BuildTotalFrame` переезжают в
реализацию `ESCPOS` — они и были её кадром.

### Автоподбор

`DisplayProbePlan` — чистая функция, отдающая упорядоченный список комбинаций:

```csharp
public sealed record DisplayProbe(int Number, IDisplayProtocol Protocol, int BaudRate);
public static IReadOnlyList<DisplayProbe> Build();   // 4 протокола x 7 скоростей = 28
```

Скорости: 600, 1200, 2400, 4800, 9600, 19200, 38400. Низ включён намеренно —
табло, гаснущее выше 2400, встречалось на живом разборе, и перебор, начинающийся
с 9600, такое не найдёт.

Порядок фиксирован и покрыт тестом: номер, который кассир увидел на табло,
обязан значить одно и то же между запусками и между версиями. Плавающий порядок
превратил бы записанное число в мусор.

Перебор гоняет `SettingsViewModel`: на каждом шаге строит `VfdDisplayService` с
комбинацией из плана и шлёт `BuildProbe(number)`. Пауза около 1.5 с на шаг, всего
порядка 42 секунд.

Формат кадра и DTR/RTS в перебор не входят и берутся из полей как есть. Они
редкие, а в кресте учетверили бы длину до 112 шагов — столько кассир не
отследит. Не нашлось с первого раза — ставятся руками, и перебор гоняется ещё
раз.

### Экран настроек

Сетка блока дисплея в
[`SettingsView.axaml`](../../../src/VvCash/Views/SettingsView.axaml) растёт с 4×2
до 4×4. Вторая пара строк: `Протокол | Формат кадра | ☑ DTR/RTS | [Подобрать]`.

Во время перебора под сеткой показывается строка состояния «12 из 28» и кнопка
«Стоп». По завершении — поле «Номер» и кнопка «Применить», которая ставит
протокол и скорость из комбинации с этим номером.

Кнопка «Проверить дисплей» остаётся на месте и в прежней роли, только шлёт кадр
уже через выбранный протокол. Три её исхода, разделённые накануне, сохраняются:
`DisplayCheckNoPort`, `DisplayCheckFailed`, `DisplayCheckOk`.

### Настройки

Три новых ключа в `settings.json`, все с откатом на нынешнее поведение:

| Ключ | Тип | По умолчанию |
|---|---|---|
| `CustomerDisplayProtocolId` | строка | пусто → `ESCPOS` |
| `CustomerDisplayFramingId` | строка | пусто → `8N1` |
| `CustomerDisplayDtrRts` | bool | `false` |

`ConfiguredCustomerDisplayService.Rebuild` начинает читать их и передавать в
`VfdDisplayService`. Подписка на `SettingsChanged` уже есть, так что смена
протокола подхватывается без перезапуска кассы — как сейчас подхватывается порт.

## Что не меняется

`ICustomerDisplayService`, `PosViewModel`, `PushToCustomerDisplay`, поведение
`NullCustomerDisplayService`, FIFO-очередь и обработка ошибок в
`VfdDisplayService`. Работа предыдущей задачи — один кадр на изменение корзины с
названием и итогом — остаётся в силе целиком.

## Тесты

- Побайтовый выход каждого из четырёх протоколов, без открытия порта.
- `ESCPOS` совпадает с зафиксированными байтами нынешней реализации.
- `NUMERIC.BuildItem` отбрасывает название и не роняет туда валюту.
- `DisplayProbePlan`: 28 комбинаций, порядок фиксирован, номер → комбинация.
- `BuildProbe` у всех четырёх протоколов содержит цифры номера и не содержит
  байтов старше 0x7F: пробник обязан читаться при неверно выбранной кодовой
  странице, иначе он проверяет заодно и её.
- `DisplayProtocols.Resolve` и `SerialFramings.Resolve`: пусто и незнакомое → `Default`.
- Round-trip трёх новых настроек через `SettingsViewModel`, по образцу тестов
  очереди (Task 24).
- `ConfiguredCustomerDisplayService` доносит протокол, формат кадра и DTR/RTS до
  собранного `VfdDisplayService` — по образцу нынешней проверки порта, скорости и
  кодовой страницы.
- Применение выбранного номера ставит протокол и скорость; отмена перебора
  прекращает отправки.

## Осознанно не делается

- **AEDEX.** Точных байтов протокола нет, проверить негде. Реализация по памяти
  удлинила бы перебор с 28 шагов до 35, могла бы не сработать и при этом
  называлась бы поддержкой. Понадобится — добавляется одной записью каталога.
- **Автоопределение успеха.** Обратной связи от табло нет, см. «Решение».
- **Ширина сегментного табло в настройках.** Пока не понадобилась; `NUMERIC`
  шлёт число без набивки.
- **Перебор формата кадра и DTR/RTS.** См. «Автоподбор».
