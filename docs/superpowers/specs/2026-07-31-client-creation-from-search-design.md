# Создание клиента из окна поиска

**Дата:** 2026-07-31
**Репозиторий:** `vv-cash` (клиент)
**Статус:** дизайн утверждён, ждёт ревью спеки

## Контекст и проблема

На кассе два входа в работу с клиентом, и оба подписаны одинаково — ключ i18n
`AddCustomer` («Добавить клиента») и иконка `AccountPlusOutline`:

- кнопка в тулбаре
  ([`PosView.axaml:187`](../../../src/VvCash/Views/PosView.axaml)) —
  `OpenCustomerRegistrationCommand`, открывает
  [`CustomerRegistrationWindow`](../../../src/VvCash/Views/CustomerRegistrationWindow.axaml);
- пилюля в шапке панели заказа
  ([`PosView.axaml:391`](../../../src/VvCash/Views/PosView.axaml)) —
  `OpenCustomerSearchCommand`, открывает
  [`CustomerSearchWindow`](../../../src/VvCash/Views/CustomerSearchWindow.axaml).

Отсюда две независимые проблемы.

**Первая — тупик в поиске.** Кассир жмёт «Добавить клиента» в чеке, ожидая
завести нового, и попадает в поиск. Окно поиска умеет только искать: `SearchCommand`,
список результатов, `ВЫБРАТЬ КЛИЕНТА`, `ОТМЕНА`
([`CustomerSearchViewModel`](../../../src/VvCash/ViewModels/CustomerSearchViewModel.cs)).
Клиента, которого нет в базе, создать неоткуда — надо закрыть окно, найти
глазами другую кнопку в тулбаре и начать заново. Пустой результат поиска при
этом никак не оформлен: `ListBox` просто пустой, без единого слова о том, что
именно произошло.

**Вторая — созданный клиент теряется.** `PosViewModel.OpenCustomerRegistration`
([`PosViewModel.cs:1435`](../../../src/VvCash/ViewModels/PosViewModel.cs))
вызывает `await dialog.ShowDialog(mainWindow)` без чтения результата, хотя
`CustomerRegistrationViewModel.SubmitAsync` возвращает созданный
`CounterpartyResponse` через `_window.Close(response)`. Клиент заводится на
сервере и молча не попадает в чек — кассир идёт искать его через поиск.

**Цель:** создание клиента должно быть доступно там, где кассир упёрся в его
отсутствие, и созданный клиент должен сразу оказываться в чеке — по обоим путям.

## Решение

Окно поиска получает два входа в регистрацию — оба дёргают одну команду:

1. **Пустое состояние.** После поиска, не давшего результатов, вместо пустого
   списка — панель «Клиент не найден» с крупной кнопкой создания.
2. **Статичная кнопка в футере.** Ряд становится
   `ОТМЕНА | + СОЗДАТЬ КЛИЕНТА | ВЫБРАТЬ КЛИЕНТА`. Видна всегда, включая случай,
   когда поиск что-то нашёл, но не того: окно 800×600 со скроллящимся списком,
   и полагаться только на пустое состояние нельзя.

Регистрация открывается **поверх окна поиска**. Успех — окно поиска закрывается
созданным клиентом, и `PosViewModel` не отличает его от выбранного из списка.
Отмена — возврат в поиск, запрос и результаты на месте.

Строка поиска переносится в форму регистрации: кассир уже набрал телефон или
имя, второй раз набирать не заставляем.

## Архитектура

### Развязка `CustomerSearchViewModel` от `Window`

Сегодня VM держит непустой `Window` в конструкторе и закрывает его сама —
из-за этого её нельзя сконструировать в тесте. В репозитории уже два обходных
пути: [`SellerSwitchViewModel`](../../../src/VvCash/ViewModels/SellerSwitchViewModel.cs)
про окно не знает вовсе, [`ReturnsViewModel`](../../../src/VvCash/ViewModels/ReturnsViewModel.cs)
принимает `Window?` и в тестах получает `null`.

Здесь второй путь не годится: создание клиента — это открытие дочернего окна,
и при `window == null` тест проверял бы ветку, которой в проде нет. Поэтому
делегаты — окно нужно вызывающей стороне, а VM хватает двух функций.

Конструктор меняется на делегаты:

```csharp
public CustomerSearchViewModel(
    ICounterpartyService counterpartyService,
    bool canCreateCustomer,
    Action<CounterpartyResponse?> close,
    Func<string, Task<CounterpartyResponse?>> createCustomer)
```

Вызов один — [`PosViewModel.cs:1414`](../../../src/VvCash/ViewModels/PosViewModel.cs);
он же подставляет `r => dialog.Close(r)` и лямбду, открывающую
`CustomerRegistrationWindow` через `ShowDialog(dialog)`, то есть модально
поверх окна поиска.

Открытие окон остаётся в `PosViewModel` — там оно живёт для всех остальных
диалогов; VM поиска о View больше не знает.

Флаг передаётся готовым `bool`, а не `ICashFeatureService`: `PosViewModel` уже
снимает его в `IsCustomerRegistrationEnabled` внутри `ApplyFeatures`, и правило
«значения снимаются при открытии экрана, а не перечитываются непрерывно» там
зафиксировано явным комментарием. Отдельное чтение сервиса в дочерней VM это
правило обходило бы.

### Пустое состояние

В VM добавляются:

```csharp
[ObservableProperty] private bool _hasSearched;

public bool HasNoResults => HasSearched && !IsLoading && SearchResults.Count == 0;
```

`HasSearched` взводится в `SearchAsync` после ответа сервиса и только при
непустом запросе — при пустом запросе метод очищает результаты и выходит рано,
и это не «не нашли», а «не искали». Без флага панель «Клиент не найден» висела
бы на свежеоткрытом окне.

`HasNoResults` пересчитывается по трём источникам: `OnHasSearchedChanged`,
`OnIsLoadingChanged` и `SearchResults.CollectionChanged` — подписка в
конструкторе, как в `SellerSwitchViewModel` для `Sellers`. Через
`CollectionChanged`, а не строкой в конце `SearchAsync`, потому что `SearchAsync`
наполняет коллекцию в несколько шагов (`Clear`, затем `Add` на результат), и
состояние должно отслеживать реальное содержимое коллекции.

`SearchResults` объявлена как `[ObservableProperty]`, то есть её можно подменить
целиком — тогда подписка осталась бы на старом объекте. `SearchAsync` коллекцию
не подменяет, только чистит и наполняет; чтобы это не сломалось молча, сеттер
перевешивает подписку в `OnSearchResultsChanged(old, new)`.

`!IsLoading` в условии гасит панель на время запроса: иначе между `Clear()` и
приходом ответа «Клиент не найден» моргает на каждом поиске.

В разметке `ListBox` показывается по `!HasNoResults`, панель пустого состояния —
по `HasNoResults`; обе в одной ячейке `Grid.Row="1"`.

### Команда создания

```csharp
[RelayCommand]
private async Task CreateCustomerAsync()
{
    var created = await _createCustomer(SearchQuery);
    if (created != null) _close(created);
}
```

`null` — отмена или ошибка создания: остаёмся в поиске, ничего не трогаем.
`CustomerRegistrationViewModel.SubmitAsync` уже возвращает `null` и при провале
запроса, так что оба случая для окна поиска неразличимы и обрабатываются
одинаково.

Обе кнопки (футер и пустое состояние) биндятся на эту команду. Обе гасятся по
`IsCreateEnabled` — то же значение `canCreateCustomer`, что уже прячет
тулбарную кнопку по флагу `cash_customer_registration_enabled`
([`CashFeatureCodes`](../../../src/VvCash/Constants/CashFeatureCodes.cs)).
Магазин, которому запрещено заводить клиентов, не должен получать обход флага
через окно поиска.

### Префилл формы регистрации

Разбор строки — чистый статический метод, отдельно от VM ради тестируемости:

```csharp
public static CustomerPrefill FromSearchQuery(string? query)
```

Правила:

- цифр в строке ≥ 10 → последние 10 цифр в `PhoneNumber` (`SubmitAsync` уже
  требует ровно 10 и сам приклеивает код страны `7`), имя не заполняется;
- иначе строка режется по пробелам: первое слово → `FirstName`, остаток
  (склеенный пробелом) → `LastName`;
- пусто или только пробелы → пустая форма.

Порог «≥ 10 цифр», а не «строка состоит только из цифр»: кассир набирает
телефон и в виде `+7 900 123-45-67`. Ровно 10 последних цифр — чтобы `+7`/`8`
в начале не сдвигали номер.

Применяется в `CustomerRegistrationViewModel` методом `ApplyPrefill(CustomerPrefill)`,
вызываемым из лямбды в `PosViewModel` сразу после создания VM, до `ShowDialog`.
Не через конструктор: у VM уже есть рабочий конструктор с двумя зависимостями,
и второй перегруз ради необязательного заполнения полей — лишняя развилка.

### Подстановка клиента в чек

Логика из `OpenCustomerSearch` (скидка по карте, `StatusMessage`,
`TriggerRequote`) выносится в `PosViewModel.ApplySelectedCustomer(CounterpartyResponse)`
и вызывается из обоих путей:

- результат окна поиска (клиент выбран из списка **или** только что создан);
- результат `OpenCustomerRegistration` из тулбара — там сегодня результат
  выбрасывается, и это чинится тем же методом.

Отдельный метод, а не копия в двух местах: правило «выбран клиент — применить
его карту и пересчитать корзину» должно жить в одном месте, иначе следующий
вход в выбор клиента про requote просто забудет, и расхождение будет молчаливым.

Три новых ключа в пять файлов
([`src/VvCash/Assets/i18n`](../../../src/VvCash/Assets/i18n)): `ru`, `en`, `kk`,
`tg`, `uz`.

| Ключ | ru |

| `CustomerNotFound` | `Клиент не найден` |
| `CustomerNotFoundHint` | `Проверьте запрос или создайте нового клиента` |

Ключи английские — как соседний `AddCustomer`, а не как транслитерированные
`[Поискклиента]`/`[ВЫБРАТЬКЛИЕНТА]`, которыми размечено окно поиска сейчас.
Существующие ключи не трогаем: их переименование — отдельная работа, не нужная
для этой задачи.

## Что не меняется

- API и `ICounterpartyService` — новых вызовов нет, используются существующие
  `SearchCounterpartiesAsync` и `CreateCounterpartyAsync`.
- Форма регистрации: поля, валидация, нумпад, размер окна.
- Тулбарная кнопка регистрации остаётся на месте — это по-прежнему прямой вход
  для случая «клиента точно нет, искать незачем».

## Принятые последствия

Модальный стек из двух окон: регистрация 1024×800 поверх поиска 800×600. Оба
центрируются по владельцу (`WindowStartupLocation="CenterOwner"`), поэтому
регистрация полностью перекрывает поиск — визуально это выглядит как переход,
а не как наслоение.

Дубль входов в регистрацию (тулбар + два места в поиске) сохраняется
сознательно: тулбар — путь «знаю, что клиента нет», поиск — путь «искал и не
нашёл». Общий у них только `cash_customer_registration_enabled`.

## Тестирование

xUnit, `CustomerSearchViewModelTest` — новый файл, VM конструируется с фейковым
`ICounterpartyService` и лямбдами-заглушками, без Avalonia:

- пустое состояние не показано на свежем окне (поиска не было);
- поиск без результатов → `HasNoResults` истинно;
- поиск с результатами → `HasNoResults` ложно;
- `IsLoading` во время запроса гасит пустое состояние;
- пустой запрос не взводит `HasSearched`;
- создание вернуло клиента → `close` вызван с ним;
- создание вернуло `null` → `close` не вызван, `SearchResults` не тронуты;
- `canCreateCustomer == false` → `IsCreateEnabled` ложно.

`CustomerPrefillTest`:

- `«7 900 123 45 67»` → телефон `9001234567`, имя пустое;
- `«89001234567»` → телефон `9001234567`;
- `«Иван»` → `FirstName = Иван`, `LastName` пусто;
- `«Иван Петров»` → `FirstName = Иван`, `LastName = Петров`;
- `«Иван Петрович Петров»` → `FirstName = Иван`, `LastName = Петрович Петров`;
- `null`, `""`, `"   "` → пустой префилл;
- `«12345»` (цифр меньше 10) → уходит в имя, не в телефон.

### Чего автотест не покрывает

`ApplySelectedCustomer` на уровне `PosViewModel` автотестом не покрывается.
В [`VvCash.Tests.csproj`](../../../tests/VvCash.Tests/VvCash.Tests.csproj) нет
mock-библиотеки, поэтому все 22 фейка для 22 зависимостей `PosViewModel` написаны
руками и лежат приватными вложенными классами внутри
[`PosViewModelSellerGateTest`](../../../tests/VvCash.Tests/PosViewModelSellerGateTest.cs)
(2095 строк). Покрыть метод можно только двумя способами: продублировать фейки в
новом файле или вынести их в общий харнесс — перенос ~500 строк тестовой
инфраструктуры, не имеющий отношения к этой задаче. Сам метод — восемь строк
линейного кода без ветвлений сверх `if (DiscountCard != null && Discount > 0)`.

Вместо теста — ручная проверка на запущенной кассе, обязательная перед мержем.
Список уточнён по итогам финального ревью и упорядочен по риску.

1. **Создание вообще проходит?** `CreateCounterpartyAsync` шлёт POST на
   `{base}users/counterparty/`, а сервер вешает этот маршрут за проверку права
   `CounterpartyCreate` (`users/routes.go`). Есть ли это право у роли кассира —
   не проверено. Рядом лежит негейтед `cash.POST("/counterparty/")`
   (`cashes/routes.go`), который клиент не зовёт. До этой задачи отказ был
   невидим — окно молча закрывалось с `null`; теперь он вылезет как «Не удалось
   создать клиента» на каждой попытке. **Этот пункт способен обнулить всю фичу,
   проверять первым, на реальной учётке кассира.**
2. На маршруте `/users/` нет `CashAuthentication`, поэтому `lctx.GetCash`
   не отрабатывает и `counterparty.CashID` остаётся пустым. Проверить, к какой
   кассе привязывается созданный клиент.
3. Геометрия окон: регистрация 1024×800 открывается поверх окна поиска 800×600
   с `CenterOwner`. На разрешении реальной кассы убедиться, что окно помещается
   целиком и футер с кнопкой «Сохранить» досягаем.
4. Поиск → пустой результат → «Создать клиента» → форма с префиллом → сохранить
   → окно поиска закрылось, клиент в чеке.
5. Поиск → «Создать клиента» в футере → отмена в форме → вернулись в поиск,
   запрос и список на месте.
6. Тулбарная кнопка регистрации → сохранить → клиент сразу в чеке (до этой
   задачи терялся).
7. Поиск → выбрать клиента с картой скидки → скидка и имя в чеке, сумма
   пересчитана.
8. Флаг `cash_customer_registration_enabled` выключен → в окне поиска нет ни
   кнопки в футере, ни кнопки в пустом состоянии, ни подсказки «создайте нового
   клиента».
9. Сохранить с включённым тумблером лояльности и посмотреть, покажет ли чек
   «Скидка по карте» или только «Выбран клиент». Ответ скажет, выдаёт ли сервер
   карту сам: `IsLoyaltyEnrolled` привязан в разметке и в C# не читается ни разу,
   а `CounterpartyCreateRequest.Discount` не заполняется. Это предсуществующая
   дыра вне объёма задачи, но именно она решает, работает ли пункт 7 для
   только что созданного клиента.
10. Формы префилла: `+7 (900) 123-45-67` → заполнен телефон, имя пустое;
    `Иван Петров` → оба поля имени. Поиск по одному телефону даёт клиента с
    `FirstName = "-"`, `LastName = "-"` — посмотреть, что тогда встаёт в чек
    как имя клиента.
11. Оборвать связь, нажать НАЙТИ: полоса ошибки появилась, прошлый список
    остался, пустого состояния нет. Кнопка «СОЗДАТЬ КЛИЕНТА» в футере при этом
    остаётся активной — это осознанно (она постоянная), но взгляд на кадр
    нужен.
