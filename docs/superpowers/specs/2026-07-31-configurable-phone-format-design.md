# Формат телефона задаётся в настройках кассы

**Дата:** 2026-07-31
**Репозиторий:** `vv-cash` (клиент)
**Статус:** дизайн утверждён, ждёт ревью спеки

## Контекст и проблема

Российский формат телефона зашит в четырёх местах:

- [`CustomerRegistrationViewModel.FormattedPhoneNumber`](../../../src/VvCash/ViewModels/CustomerRegistrationViewModel.cs) —
  строка `"+7 (___) ___-__-__"` и тридцать строк ручной сборки формата;
- `CustomerRegistrationViewModel.Numpad` — нумпад не принимает больше десяти цифр;
- `CustomerRegistrationViewModel.SubmitAsync` — на сервер уходит `$"7{PhoneNumber}"`
  и только при длине ровно десять;
- [`CustomerPrefill.FromSearchQuery`](../../../src/VvCash/Models/CustomerPrefill.cs) —
  строка поиска считается телефоном от десяти цифр, берутся последние десять.

При этом приложение возит локали `ru`, `en`, `kk`, `tg`, `uz`
([`src/VvCash/Assets/i18n`](../../../src/VvCash/Assets/i18n)). Национальный номер
в Таджикистане — девять цифр после `+992`, в Узбекистане — девять после `+998`.

Отсюда: **на таджикской или узбекской кассе местный номер ввести нельзя вообще.**
Нумпад ждёт десятую цифру, которой в номере нет, поэтому `PhoneNumber.Length == 10`
никогда не выполняется, и `SubmitAsync` тихо отправляет `Phone = null`. Клиент
заводится без телефона, кассир об этом не узнаёт.

**Цель:** формат телефона выбирается на экране настроек кассы и определяет ввод,
отображение и то, что уходит на сервер.

## Решение

На экране настроек — выпадающий список стран рядом с выбором языка. Выбранное
значение хранится локально в файле настроек и снимается окном регистрации при
открытии.

Не с сервера: маска нужна на кассе, которая может открыться до первой
синхронизации, и требовать ради неё работы в отдельном репозитории бэкенда
несоразмерно. Не по языку интерфейса: язык и страна — разные вещи, и
русскоязычный кассир в Душанбе получил бы `+7`.

## Архитектура

### Каталог форматов

Новый `src/VvCash/Models/PhoneFormat.cs` — чистый тип без зависимостей, по образцу
[`CustomerPrefill`](../../../src/VvCash/Models/CustomerPrefill.cs):

```csharp
public sealed class PhoneFormat
{
    public PhoneFormat(string id, string displayName, string countryCode, string mask);

    public string Id { get; }          // то, что ложится в настройки
    public string DisplayName { get; }
    public string CountryCode { get; } // приклеивается к номеру при отправке
    public string Mask { get; }        // только национальная часть
    public int DigitCount { get; }     // считается из Mask в конструкторе
}
```

Конструктор, а не `init`-свойства как у `CustomerPrefill`: `DigitCount`
вычисляется из `Mask` один раз, а объект с `init`-свойствами вычислить его при
создании не может. Записи каталога строятся только в коде и никогда не
десериализуются, так что терять поддержку object initializer здесь нечего.

Три записи в статическом каталоге `PhoneFormats.All`:

| Id | Показывается | Код | Маска | Цифр |
|---|---|---|---|---|
| `RU` | +7 — Россия / Казахстан (RU / KZ) | 7 | `(###) ###-##-##` | 10 |
| `TJ` | +992 — Таджикистан (TJ) | 992 | `(##) ###-##-##` | 9 |
| `UZ` | +998 — Узбекистан (UZ) | 998 | `(##) ###-##-##` | 9 |

Казахстан не отдельной записью: там тот же `+7` и те же десять цифр, отдельный
пункт делал бы вид, что выбор на что-то влияет.

`DisplayName` не переводится и лежит в коде, но строка построена так, чтобы это
не было проблемой. Первая редакция спеки утверждала, что названия стран
одинаково читаются на всех пяти языках, — это неверно: узбекская локаль
латинская, английская тоже, и выпадающий список целиком кириллицей их кассир не
прочтёт. Хуже всего было бы с «Россия / Казахстан»: весь смысл записи — «два
случая под одним кодом» — жил в нелатинской части.

Поэтому впереди идёт код набора, который от письменности не зависит и сам по
себе достаточен для выбора, а латинские ISO-коды в скобках делают запись
опознаваемой в `en` и `uz`. Пятнадцать ключей i18n это не покупает — цена нулевая.

### Две функции на маске

В `Mask` символ `#` — место под цифру, всё остальное литерал.

- `Format(string digits)` — заполняет `#` слева направо введёнными цифрами,
  незаполненные заменяет на `_`, приклеивает `+{CountryCode} ` спереди. Частичный
  ввод `9012` при маске `TJ` даёт `+992 (90) 12_-__-__`.
- `Placeholder` — то же при пустом вводе: `+992 (__) ___-__-__`.

Обе чистые и покрываются тестами без Avalonia. Они же заменяют ручную сборку
строки в `FormattedPhoneNumber`, которая сегодня занимает тридцать строк и
существует ровно для одной страны.

`DigitCount` считается из `Mask` в конструкторе, а не хранится отдельным полем:
два источника одной правды разъехались бы при первой же правке маски.

### Хранение и экран настроек

`SettingsData.PhoneFormatId` (string, по умолчанию пусто), `ISettingsService.PhoneFormatId`,
и `ComboBox` в [`SettingsView.axaml`](../../../src/VvCash/Views/SettingsView.axaml)
рядом с выбором языка — стиль `SettingsCombo` уже есть.

Отличие от списка языков: там `ObservableCollection<string>` и `SelectedItem`
привязан прямо к строке. Здесь коллекция из `PhoneFormat` и `ItemTemplate` на
`DisplayName`, чтобы в настройках лежал `Id`, а не показанное название —
переименование страны в интерфейсе не должно ломать сохранённую настройку.

Разрешение идентификатора в формат — чистая функция каталога
`PhoneFormats.Resolve(string? id)`: пустое, неизвестное или отсутствующее значение
даёт `RU`. Это и миграция существующих касс, и защита от настройки, оставшейся от
удалённой записи каталога — касса не должна оставаться без формата ни при каком
содержимом файла. Функцией, а не веткой `??` на месте использования, чтобы
правило было одно и проверялось тестом без файловой системы.

### Кто маску потребляет

`CustomerRegistrationViewModel` получает `ISettingsService` третьим параметром
конструктора и снимает формат один раз при создании — как `PosViewModel` снимает
фича-флаги в `ApplyFeatures`. Три точки:

- `FormattedPhoneNumber` → `_format.Format(PhoneNumber)`;
- `Numpad` → предел `_format.DigitCount`;
- `SubmitAsync` → `_format.CountryCode + PhoneNumber`.

Единственный вызывающий — `PosViewModel.ShowCustomerRegistrationAsync`, где
`_settingsService` уже есть.

`CustomerPrefill.FromSearchQuery` получает второй параметр `digitCount`: порог
«это телефон» и длина среза берутся из него. Без этого на таджикской кассе
девятизначный номер из строки поиска не опознался бы телефоном и уехал в имя.
Вызывающий тот же `PosViewModel`.

## Попутная правка: неполный телефон больше не теряется

Сегодня `SubmitAsync` при неполной длине отправляет `Phone = null` и закрывает
окно успехом. Кассир, набравший восемь цифр из девяти, получает клиента без
телефона и никакого сигнала.

Это тот же класс, что закрывался в
[предыдущей спеке](2026-07-31-client-creation-from-search-design.md): молчаливая
потеря вместо отказа. `SubmitAsync` будет отказываться отправлять форму,
показывая `ErrorMessage` — механизм для этого уже добавлен в ту задачу — и
оставлять окно открытым.

Пустой телефон при этом остаётся законным: клиент без телефона — нормальная
запись, отказ должен ловить именно **начатый и не дописанный** номер.

Нужен новый ключ i18n `PhoneIncomplete` в пять файлов.

## Что не меняется

- Телефоны существующих клиентов в списке результатов поиска показываются как
  пришли с сервера. Форматировать их по локальной маске нельзя: клиент мог быть
  заведён в другой стране.
- Формат отправки на сервер: по-прежнему код страны и цифры без разделителей,
  меняется только сам код.
- Каталог не редактируется из интерфейса. Новая страна — правка кода и релиз;
  выбрано сознательно, чтобы кассир не мог задать маску, которой не бывает.

## Тестирование

xUnit, без Avalonia.

`PhoneFormatTest`:

- `DigitCount` равен числу `#` для каждой из трёх записей каталога;
- `Format` на пустом вводе равен `Placeholder`;
- `Format` на частичном вводе: цифры слева, `_` справа, литералы на местах;
- `Format` на полном вводе не оставляет ни одного `_`;
- `Format` игнорирует лишние цифры сверх `DigitCount`;
- каталог: `Id` уникальны, ни одного пустого `CountryCode` или `Mask`.

`CustomerPrefillTest` — существующие случаи параметризуются по `digitCount`,
добавляются девятизначные: `«992 90 123 45 67»` при `digitCount = 9` даёт телефон
`901234567`, а не имя.

`PhoneFormats.Resolve` (в том же `PhoneFormatTest`) — `null`, пустая строка,
неизвестный `Id` и `Id` в другом регистре дают `RU`; известный `Id` даёт свою
запись.

`SettingsDefaultsTest` — дополняется одним фактом: `new SettingsData().PhoneFormatId`
пуст. Файловый round-trip не проверяется: этот тест-класс намеренно работает с
`SettingsData` напрямую, а всё поведение, которое может сломаться, живёт в
`Resolve`, а не в сериализации ещё одной строки рядом с девятью такими же.

### Чего автотест не покрывает

`CustomerRegistrationViewModel` — конструктор требует непустой
`Avalonia.Controls.Window`, поэтому ни привязка формата к нумпаду, ни отказ на
неполном номере автотестом не проверяются. Ручная проверка на кассе:

1. Настройки → выбрать Таджикистан → сохранить → открыть регистрацию: плейсхолдер
   `+992 (__) ___-__-__`, нумпад останавливается на девятой цифре.
2. Ввести полный номер, сохранить, проверить в базе, что телефон записан с `992`.
3. Ввести восемь цифр, нажать «Сохранить» → окно осталось открытым, показано
   сообщение, введённое не потеряно.
4. Оставить телефон пустым и сохранить → клиент создаётся.
5. Поиск по девятизначному номеру → «Создать клиента» → телефон подставился в
   форму, имя пустое.
6. Вернуть Россию → плейсхолдер и предел вернулись к десяти цифрам.
7. Обновление существующей кассы, где настройка не задана → формат `RU`, поведение
   не изменилось.
