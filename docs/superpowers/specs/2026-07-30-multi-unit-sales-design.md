# Продажа во вторичных единицах измерения на кассе

Дата: 2026-07-30
Статус: дизайн

## Задача

Бэкенд умеет продавать товар во вторичной единице (м², пог. м, кг). Касса не
умеет ничего: `Product` не имеет полей единицы, синк их не разбирает, документ
продажи не отправляет. Кассир не может задать «12.5 м² плитки» — только «53
штуки», посчитав в уме.

## Модель, как её задумал сервер

Базовая единица — всегда штука. `quantity` в строке документа — всегда штуки,
и это не меняется. Вторичная единица — способ ввода плюс снимок в строке
документа.

- `secondary_unit_factor` — сколько вторичных единиц в одной штуке (0.24 м² на
  плитку).
- `is_divisible` — можно ли продать дробную штуку.
- Строка документа несёт тройку `unit_id` / `unit_factor` / `quantity_in_unit`:
  все три или ни одной.

Сервер проверяет снимок: `unit_id` должен совпасть с единицей товара, а
`|quantity_in_unit − quantity × factor|` не превысить `ToleranceFor(factor)` =
`max(0.001, factor × 1e-6)`. Для продажи с кассы (`sold_source = cash`) сервер
доверяет `unit_factor`, присланному кассой, а не своей карточке: касса могла
быть офлайн, когда фактор поменяли, а чек уже напечатан.

## Решения

| Вопрос | Решение |
| --- | --- |
| Единица ввода | Явный переключатель `шт` / `м²` — зависит от товара |
| Дефолт переключателя | Новое поле на карточке товара, едет в синк |
| Цена на экране | Следует единице ввода: ввод в м² → «416.67 / м²» |
| Округление вверх | Живой пересчёт в numpad, без модалок |
| Возврат и обмен | Вне этой спеки, остаются в штуках |
| Feature-флаг | Не нужен: фичу гатят сами данные |

Фича включается заполнением вторичной единицы на карточке товара. У товара без
`secondary_unit_id` на кассе не меняется ровно ничего.

## Компоненты

### 1. `UnitConverter` — новый, `src/VvCash/Services/UnitConverter.cs`

Точное зеркало `units.ConvertToBase` / `units.ConvertToUnit` с сервера. Живёт
отдельно от корзины: это чистая арифметика без зависимостей, её проверяют
таблицей значений, и она обязана совпасть с Go до последнего знака — иначе
сервер отвергнет собственный честный чек по допуску.

```csharp
public static (decimal Quantity, decimal QuantityInUnit) ToBase(
    decimal amount, decimal factor, bool isDivisible)
```

- Делимый: `Quantity = amount / factor`, округлённый до 6 знаков
  (`divisibleScale` на сервере), `QuantityInUnit = amount` — ровно то, что
  кассир набрал. Округление половины — от нуля: серверный `DivRound` округляет
  именно так, то есть `Math.Round(x, 6, MidpointRounding.AwayFromZero)`, а не
  банковское округление по умолчанию в .NET.
- Неделимый: целое число штук с округлением **вверх**, `QuantityInUnit`
  пересчитывается как `штуки × factor`. Клиент платит за целые штуки.

Округление вверх считать через точный остаток, не через `Math.Ceiling` от
частного:

```csharp
var pieces = decimal.Truncate(amount / factor);
if (pieces * factor < amount) pieces += 1;
```

`decimal` делит с округлением на 28-й значащей цифре. На ходовых факторах вроде
0.24 частное представимо точно и `Math.Ceiling` сработал бы, но при мелком
факторе и большом количестве частное в 28 цифр не укладывается и может
округлиться вверх — тогда `Math.Ceiling` добавит лишнюю штуку в чек. Умножение
`decimal` точное, поэтому сравнение остатка надёжно при любом факторе. Это же
делает сервер: `QuoRem` в целочисленной арифметике, а не `Div` через
изменяемую глобальную `decimal.DivisionPrecision`.

`factor <= 0` и `amount <= 0` — ошибка, как на сервере.

### 2. `Product` — новые поля

`UnitId`, `UnitCode`, `UnitShortName`, `UnitFactor` (decimal), `IsDivisible`,
`SellInSecondaryUnit`. Плюс `HasSecondaryUnit => UnitId != "" && UnitFactor > 0`.

`UnitFactor` разбирать в `decimal`, а не `double`: он идёт в сравнение с
серверным допуском, и накопленный дрейф двоичного плавающего сложится с
`quantity × factor` на строке в сотню штук.

### 3. `SyncService` — разбор новых ключей

[SyncService.cs:213](../../../src/VvCash/Services/Data/SyncService.cs) читает
`unit_id`, `unit_code`, `unit_short_name`, `unit_factor`, `is_divisible`,
`sell_in_secondary_unit`. Отсутствующий ключ — товар поштучный: старый бэкенд
не должен ломать синк.

### 4. `OfflineStorageService` — 6 новых колонок

`Products` получает `UnitId`, `UnitCode`, `UnitShortName`, `UnitFactor`,
`IsDivisible`, `SellInSecondaryUnit` через ту же идиому
`ALTER TABLE ... ADD COLUMN` в try/catch, что уже применена для `Tags`
([OfflineStorageService.cs:130](../../../src/VvCash/Services/Data/OfflineStorageService.cs)).
`ReadProduct` читает по ординалам — новые колонки идут в конец, существующие
ординалы не сдвигаются.

### 5. `CartItem` — режим ввода и снимок

- `EnteredInUnit` (bool, observable) — в какой единице кассир ввёл строку.
- `QuantityInUnit` (decimal) — **хранимое** поле, не вычисляемое.

Хранимое, потому что у делимого товара `QuantityInUnit` — это ровно то, что
набрал кассир (12.5), а `Quantity × factor` даст 12.49999992 после среза до 6
знаков. Сервер пропустит оба по допуску, но в чеке клиент должен увидеть 12.5.
У неделимого оба совпадают точно.

`Quantity` остаётся штуками и остаётся источником истины для денег: `LineTotal`,
`PromotionCalculator`, `QuoteRequestBuilder` не трогаем вовсе.

### 6. `CartService`

- `AddItem` ставит `EnteredInUnit = product.SellInSecondaryUnit && HasSecondaryUnit`,
  количество — 1 штука. Тап по товару кладёт одну штуку; точное количество
  кассир задаёт в numpad.
- Новый `SetQuantityInUnit(item, amountInUnit)` → `UnitConverter.ToBase` →
  пишет `Quantity` и `QuantityInUnit`.
- `SetQuantity` (штуки) остаётся и пересчитывает `QuantityInUnit = Quantity × factor`.
- `IncreaseQuantity` / `DecreaseQuantity` шагают **на одну штуку** независимо от
  режима: `+` на плитке добавляет плитку, а не квадратный метр.

### 7. Numpad количества — новый

Сегодня в UI его нет: `SetQuantity` вызывается только из тестов, в корзине
живут одни `+`/`−` ([PosView.axaml:454](../../../src/VvCash/Views/PosView.axaml)).
Строится с нуля.

- Открывается тапом по числу количества в строке корзины.
- Переключатель `шт` / `<short_name>`; для товара без вторичной единицы
  переключателя нет, поведение как сегодня.
- Живой пересчёт под полем ввода. Кассир набирает `12.5` в режиме м²:
  `→ 53 шт = 12.72 м² · 5300.00`. Строка обновляется на каждое нажатие, до
  подтверждения.
- Цена в шапке следует переключателю: `416.67 / м²` либо `100.00 / шт`, где
  цена за единицу = `Price / UnitFactor`.
- В режиме штук у неделимого товара дробный ввод отклоняется.

### 8. Документ продажи

Строка в [DocumentRequest.cs](../../../src/VvCash/Models/Api/DocumentRequest.cs)
получает nullable `unit_id`, `unit_factor`, `quantity_in_unit`. Отправляются
только когда `HasSecondaryUnit`, и только все три сразу — сервер отвергает
частичную тройку. `quantity` остаётся штуками.

`unit_factor` шлём тот, что пришёл в синке, а не пересчитанный: сервер именно
его и ждёт от кассы как исторический факт напечатанного чека.

### 9. Чек и дисплей покупателя

Строка чека дополняется величиной во вторичной единице, когда она есть:
`53 шт × 100.00 = 5300.00` и ниже `12.72 м²`. Так же в
`CustomerDisplayWindow`. У поштучного товара вид строки не меняется.

### 10. Отложенные продажи

`ParkedCartItem` получает `EnteredInUnit` и `QuantityInUnit`. Payload — JSON,
схему `ParkedSales` менять не нужно. Строка, отложенная в м², должна вернуться
из отложенных в м².

## Порядок данных

```
cash sync (unit_id, unit_code, unit_short_name, unit_factor,
           is_divisible, sell_in_secondary_unit)
   ↓
Product  →  SQLite Products
   ↓
numpad: ввод в м²  →  UnitConverter.ToBase  →  (Quantity шт, QuantityInUnit м²)
   ↓
CartItem.Quantity (штуки)  →  деньги, промо, quote  — без изменений
CartItem.QuantityInUnit    →  чек, дисплей, тройка в документе
   ↓
POST документа: quantity=53, unit_id, unit_factor=0.24, quantity_in_unit=12.72
```

## Ошибки

- Товар без вторичной единицы: тройка не отправляется, UI как сегодня.
- `UnitFactor` пришёл нулевым или отрицательным при непустом `UnitId`: считаем
  товар поштучным, переключатель не показываем. Битая карточка не должна ронять
  продажу.
- Сервер отверг снимок: документ уходит в очередь неотправленных, как любая
  другая ошибка отправки. Отдельной обработки не вводим.
- Старый бэкенд без полей единицы: все товары читаются поштучными.

## Тесты

`UnitConverterTest` — ядро, таблицей значений:

- делимый: 12.5 / 0.24 → 52.083333 шт, 12.5 м²;
- неделимый: 12.5 / 0.24 → 53 шт, 12.72 м²;
- точное кратное: 12.0 / 0.24 → 50 шт, 12.0 м² — **не** 51;
- округление до 6 знаков совпадает с серверным `DivRound`, включая половину
  (округление от нуля, не банковское);
- каждый случай дополнительно проверяется на серверный инвариант
  `|QuantityInUnit − Quantity × factor| ≤ max(0.001, factor × 1e-6)`;
- `factor <= 0` и `amount <= 0` — ошибка.

`CartServiceTest` — `SetQuantityInUnit` пишет обе величины; `+`/`−` шагают
штуками в режиме м²; `AddItem` берёт режим из `SellInSecondaryUnit`;
`SetQuantity` пересчитывает `QuantityInUnit`.

`SyncService` — разбор новых ключей и их отсутствия.

`OfflineStorageService` — round-trip товара с единицей и без.

`DocumentRequest` — тройка присутствует целиком либо отсутствует целиком.

`EscPos` — строка с единицей и без.

## Вне границ

- Возврат и обмен. Работают на `int Quantity`
  ([ReturnModels.cs:57](../../../src/VvCash/Models/Api/ReturnModels.cs)); перевод
  на единицы потребует `decimal` в моделях возврата и правок на сервере.
  Отдельная задача.
- Feature-флаг. Фичу гатят данные карточки товара.
- Ввод количества с весов. Numpad — ручной ввод; интеграция с весами не
  рассматривается.

## Зависимости от бэкенда

Сделано:

- `unit_id` в синке кассы — `CashProductItem` и `CashProductResult`, обе выборки
  (`GetProductsForVersion`, `GetProductFromBarcode`). Без него касса не может
  собрать валидную тройку: сервер сверяет `unit_id` с единицей товара.

Требуется до релиза:

- Поле «продавать во вторичной единице» (`sell_in_secondary_unit`): миграция,
  API товара, синк кассы, поле в бэк-офисе (репозиторий `bozor`).

Пока поля нет, касса берёт дефолтом вторичную единицу для любого товара с
`HasSecondaryUnit`. Это работает, но кассир будет переключать на штуки вручную
там, где товар считают штуками.
