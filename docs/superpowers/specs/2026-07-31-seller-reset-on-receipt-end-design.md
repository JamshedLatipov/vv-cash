# Сброс продавца по завершении чека

**Дата:** 2026-07-31
**Репозиторий:** `vv-cash` (клиент)
**Статус:** дизайн утверждён, ждёт ревью спеки

## Контекст и проблема

Мультипродавец на кассе реализован по спеке
[2026-07-27](2026-07-27-multi-seller-pin-auth-design.md): кто продаёт — хранит
[`SellerSession`](../../../src/VvCash/Services/SellerSession.cs), подтверждение
личности — PIN по локальному ростеру, `seller_id` уходит в
[`DocumentRequest`](../../../src/VvCash/Models/Api/DocumentRequest.cs).

Сегодня `SellerSession.Current` обнуляется только в трёх случаях:

- закрытие смены — `PosViewModel.DoCloseShiftAsync`;
- выход/отзыв сессии по 401 — `PosViewModel.PerformSignOut`;
- обновление ростера, если продавца там больше нет или он потерял `can_sell` —
  `SellerSession.LoadRosterAsync`.

Между чеками сброса нет. Единственная защита — идл-таймаут 90 секунд
([`SellerSessionConstants.IdleTimeout`](../../../src/VvCash/Constants/SellerSessionConstants.cs)):
`IsStale` заставляет переспросить PIN в начале нового чека
(`PosViewModel.AddToCart`, `PosViewModel.ResumeParkedSale`), а таймер продлевает
каждое добавление товара.

Отсюда дыра, ради закрытия которой вся фича и делалась: продавец A завершил
оплату, к кассе подошёл продавец B и начал следующий чек раньше, чем истекли 90
секунд с последнего `Touch()` — продажа уйдёт на A, молча и без единого признака
на экране (в шапке всё это время висит имя A).

**Цель:** конец чека — точка, после которой личность нужно подтверждать заново,
независимо от таймера.

## Решение

Завершение операции на кассе сбрасывает продавца жёстко:
`SellerSession.Clear()`, то есть `Current = null` + событие `CurrentChanged`.
Чип в шапке немедленно превращается в «Кто продаёт?»
(`PosViewModel.SellerChipText`), а следующий товар в пустую корзину гарантированно
поднимает оверлей выбора продавца — `IsStale` при `Current == null` истинно по
определению.

Идл-таймаут остаётся как есть: он теперь второй рубеж — на случай чека, брошенного
на середине.

### Точки сброса

1. **Успешная оплата** — `PosViewModel.Pay`, success-ветка
   `CreateExpenseDocumentAsync` (рядом с `_approvedById = null`). Только success:
   провал оплаты оставляет продавца, чтобы повтор не требовал повторного PIN.
   Документ, ушедший в офлайн-очередь, считается успехом — он уже несёт
   `seller_id`.
2. **Ручная очистка чека** — команда `PosViewModel.ClearCart`.
3. **Возврат** — после закрытия `ReturnsWindow`, если внутри был проведён хотя бы
   один возврат.
4. **Обмен** — после закрытия `ExchangeWindow`, если внутри был записан хотя бы
   один документ.

### Точки, где сброса намеренно нет

- **Откладывание чека (park).** Отложенный чек — пауза, а не конец работы
  продавца; при возобновлении гейт `ResumeParkedSale` и так переспрашивает, если
  сессия протухла.
- **Авто-park внутри `ResumeParkedSale`.** Это середина одной операции, не её
  конец.
- **Провал оплаты, отменённый диалог возврата/обмена.** Ничего не завершилось.

## Архитектура

### Choke point в `PosViewModel`

Все четыре точки зовут один приватный метод — по образцу уже существующего
`PerformSignOut`, единственной точки выхода из сессии:

```csharp
private void EndReceipt() => _sellerSession.Clear();
```

Почему не прямые вызовы `_sellerSession.Clear()` в четырёх местах: смысл «чек
закончился, личность больше не подтверждена» должен жить в одном месте с
объяснением — иначе следующая точка завершения чека (например, будущий вариант
оплаты) просто забудет про сброс, и расхождение будет молчаливым.

Почему не метод в `SellerSession` (`EndSale()`): сервис отвечает за «кто за
кассой», а не за жизненный цикл чека. `Clear()` у него уже есть, добавлять
чек-специфичный синоним — размывать границу.

### Флаг завершения в диалогах

`ReturnsWindow` и `ExchangeWindow` — модальные (`await dialog.ShowDialog`), так
что результат читается по возврату из `ShowDialog`, без событий.

Обе VM получают публичное свойство:

```csharp
public bool CompletedDocument { get; private set; }
```

Липкое (однократно `true`, никогда не сбрасывается): окно живёт одну операцию, а
несколько проведённых возвратов подряд — всё равно «документ был».

- `ReturnsViewModel.SubmitReturn` — ставится после успешного
  `CreateReturnAsync`, рядом с `SuccessMessage`.
- `ExchangeViewModel.SubmitExchange` — ставится там же, где выставляется
  `_returnBooked = true`, то есть в момент, когда на сервере впервые что-то
  записано. Обмен трёхшаговый (возврат → выплата из кассы → продажа), и если
  возврат прошёл, а выплата упала, документ всё равно уже есть — сбрасывать
  надо.

`PosViewModel.ShowReturnsDialogAsync` и `PosViewModel.OpenExchange` держат ссылку
на созданную VM, после `ShowDialog` читают флаг и при `true` зовут `EndReceipt()`.

### Взаимодействие с выключенным переключением продавцов

Отдельный guard на `IsSellerSwitchEnabled` не нужен: при выключенном флаге
`Current` всегда `null`, а `SellerSession.Clear()` при `Current == null` —
ранний `return` без события. Сброс вырождается в no-op сам собой.

## Принятые последствия

Сразу после оплаты `Current == null`, поэтому закрытие смены (`CanCloseShift`) и
открытие возвратов (`CanRefund`) уйдут в PIN-апрув, пока продавец не подтвердится
снова. Это прямая цена жёсткого сброса и она принята: оба действия и без того
задуманы как «fail closed при неподтверждённой личности».

Дополнительных сетевых вызовов и изменений API нет; `SellerSession`, ростер и
бэкенд не меняются.

## Тестирование

xUnit, по образцу `PosViewModelSellerGateTest` (фейковый `ISellerSession`,
проверка `Clear()`):

- успешная оплата → продавец сброшен;
- провал создания документа → продавец не сброшен;
- `ClearCart` → продавец сброшен;
- `EndReceipt` при выключенном переключении → `Current` остаётся `null`, событий
  нет (регресс-защита на no-op);
- `ReturnsViewModel`: успешный возврат ставит `CompletedDocument`, неуспешный —
  нет;
- `ExchangeViewModel`: `CompletedDocument` выставляется, как только возврат
  записан, даже если следующий шаг упал;
- после сброса первый `AddToCart` в пустую корзину поднимает
  `SellerSwitchRequested` немедленно, без ожидания идл-таймаута.
