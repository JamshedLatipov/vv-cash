# Печать и железо (батч B код-ревью)

**Дата:** 2026-08-22
**Репозиторий:** `vv-cash`. Бэкенд не затрагивается.
**Статус:** дизайн утверждён, ждёт ревью спеки

## Контекст

Второй из четырёх батчей, на которые разрезано код-ревью кассы. Батч A
([спека](2026-08-22-session-and-data-safety-design.md)) закрыл сессию и сохранность
данных. Этот закрывает ввод-вывод с железом:

| # | Находка |
|---|---|
| 3 | ESC/POS шлёт UTF-8 без выбора кодовой страницы — кириллица печатается мусором |
| 4 | USB-печать — заглушка, которая рапортует успех |
| 13 | Дробное количество на чеке обмена печатается как целое |
| 15 | `MockCustomerDisplayService` зарегистрирован как боевой; `VfdDisplayService` мёртв |
| 10 | `CompositePrinterService` пересобирает список принтеров во время печати |

Находка 10 была отнесена к батчу D и перенесена сюда сознательно — см. её раздел.

### Что известно про парк

Ничего. Инвентаря нет ни в бэкенде (`cashes/config_models.go` знает только legacy-строки
без структуры), ни в документации, ни в истории коммитов. Единственное прямое
свидетельство — настройки этой машины:

```json
"Printers": [{ "ConnectionType": 0, "ConnectionString": "4BARCODE 4B-2053A", "IsEnabled": true }]
```

`ConnectionType: 0` — это `USB` (`PrinterConnectionType { USB, COM, LAN }`). То есть касса
разработчика настроена ровно на тот путь, который является заглушкой.

Отсюда порядок важности: **#4 важнее #3**. Кодовая страница имеет значение только после
того, как байты начнут доходить до принтера.

## Проблема 1 — USB-печать не печатает и скрывает это

[`EscPosPrinterService.SendViaUsb`](../../../src/VvCash/Services/Hardware/EscPosPrinterService.cs)
пишет в консоль и возвращает завершённую задачу:

```csharp
private Task SendViaUsb(byte[] data)
{
    // For USB raw printing, integrating with Windows Spooler API via PInvoke is required.
    // As a fallback/stub for now, we just output to console ...
    Console.WriteLine($"[USB Printer '{_connectionString}'] Outputting {data.Length} bytes.");
    return Task.CompletedTask;
}
```

`PrintReceiptAsync` не отличает это от успеха, поэтому возвращает `true`, а кассир читает
«Receipt printed» над принтером, который ничего не напечатал.

### Решение

[`PrinterDiscoveryService.GetUsbPrinters`](../../../src/VvCash/Services/Hardware/PrinterDiscoveryService.cs)
уже перечисляет **имена принтеров Windows** через WMI `Win32_Printer` — значит
`ConnectionString` для USB это имя в спулере, и слать надо туда же, сырым потоком:

```
OpenPrinter(name) → StartDocPrinter(DOCINFO1{ pDataType = "RAW" })
                  → StartPagePrinter → WritePrinter(bytes) → EndPagePrinter
                  → EndDocPrinter → ClosePrinter
```

Интероп живёт в отдельном `Services/Hardware/WindowsRawPrinter.cs` с единственным
публичным методом `Send(string printerName, byte[] data)`, чтобы `EscPosPrinterService`
остался про ESC/POS, а не про маршалинг.

Три места, где это легко сделать неправильно:

- **Каждый вызов winspool возвращает `bool`.** Игнорировать их — воспроизвести нынешнюю
  ложь на новом уровне. На `false` берётся `Marshal.GetLastWin32Error()` и бросается
  исключение; существующий `catch` в `PrintReceiptAsync` выставит `PrinterStatus.Error` и
  вернёт `false`.
- **Неуправляемая память освобождается в `finally`**, дескриптор принтера закрывается там же.
- **Проект таргетит `net10.0`, не `net10.0-windows`.** Нужен
  `RuntimeInformation.IsOSPlatform(OSPlatform.Windows)` и `[SupportedOSPlatform("windows")]`,
  иначе анализатор выдаст CA1416. На не-Windows USB-путь честно сообщает, что не
  поддержан, — молчать он больше не должен нигде.

Главное здесь — не сам интероп, а то, что USB перестаёт рапортовать успех.

## Проблема 2 — кодовая страница

[`EscPosPrinterService.WriteLine`](../../../src/VvCash/Services/Hardware/EscPosPrinterService.cs)
кодирует текст в UTF-8, а инициализация ограничена `ESC @`; команды `ESC t n` нет нигде в
проекте. Термопринтеры ESC/POS работают на однобайтовых кодовых страницах, поэтому русские
названия товаров печатаются мусором.

### Блокер, который легко пропустить

В .NET Core однобайтовых кодировок нет из коробки: `Encoding.GetEncoding(866)` бросает
`NotSupportedException`, пока не подключён пакет `System.Text.Encoding.CodePages` и не
зарегистрирован провайдер. Регистрация идёт в `Program.Main` **до** `BuildAvaloniaApp()`,
рядом с `RenderingSelector` — оба решаются до появления UI:

```csharp
Encoding.RegisterProvider(CodePagesEncodingProvider.Instance);
```

Без этой строки первая же попытка напечатать чек падает.

### Каталог

По образцу [`PhoneFormats`](../../../src/VvCash/Models/PhoneFormat.cs) и с той же
политикой: список живёт в коде, из интерфейса не редактируется, новая запись — правка файла
и релиз. Кассир не должен иметь возможности задать таблицу, которой у принтера нет.

```csharp
public sealed class EscPosCodePage
{
    public string Id { get; }            // "CP866" — ложится в настройки
    public string DisplayName { get; }   // "CP866 — кириллица (DOS)"
    public int CodePage { get; }         // 866 → Encoding.GetEncoding
    public byte EscTSelector { get; }    // n в ESC t n
}
```

Обе части записи нужны и по разным причинам: `CodePage` определяет, **какие байты** уходят,
`EscTSelector` — **как принтер их истолкует**. Разойдутся — получится другой мусор вместо
нынешнего.

Стартовый набор и значения `EscTSelector` — из нумерации таблиц Epson, которой следует
большинство клонов:

| Id | .NET codepage | `ESC t n` | Уверенность |
|---|---|---|---|
| `CP866` | 866 | 17 | высокая — таблица «Cyrillic #2», поддержана почти повсеместно |
| `CP1251` | 1251 | 46 | **низкая** — у клонов встречаются 6, 7 и 46 |
| `PC437` | 437 | 0 | высокая — латиница, таблица по умолчанию у всех |

Разброс в строке `CP1251` — не небрежность, а вторая причина, по которой этот выбор вынесен
в настройку с пробной печатью: угадать его из репозитория невозможно.

### Где хранится

Поле `PrinterConfig`, то есть **на принтер**, а не на кассу: в магазине могут стоять две
разные железки. У VFD своя, отдельная — см. проблему 3.

Дефолт — CP866: именно её понимают большинство ESC/POS-клонов на этом рынке.

### Честная граница

Номер таблицы в `ESC t n` у разных производителей различается, и проверить его отсюда
нечем. Каталог — это стартовый набор гипотез, а арбитром выступает пробная печать на точке.
Если ни одна запись не подошла, это правка каталога и релиз — ровно как с форматами
телефона.

## Проблема 3 — VFD-дисплей покупателя

[`ICustomerDisplayService`](../../../src/VvCash/Services/Hardware/ICustomerDisplayService.cs)
живой: пять вызовов из `PosViewModel` на добавление товара, изменение корзины, очистку и
оплату. Но зарегистрирован
[`MockCustomerDisplayService`](../../../src/VvCash/Services/Hardware/MockCustomerDisplayService.cs),
поэтому всё это уходит в `Console.WriteLine`.
[`VfdDisplayService`](../../../src/VvCash/Services/Hardware/VfdDisplayService.cs) не
создаётся нигде и не имеет настроек — их просто никогда не сделали.

Помимо этого в нём три дефекта:

| Дефект | Следствие |
|---|---|
| `Encoding.ASCII` | кириллица превращается в `?` |
| `$` зашит в `ShowItemAsync`/`ShowTotalAsync` | та же болезнь, что уже чинили на чеке |
| нет команды инициализации | строки не сбрасываются, дисплей копит мусор |

### Решение

**Настройки:** порт, скорость, кодовая страница из каталога. Скорость — потому что 9600
сейчас зашито, а VFD встречаются на 2400 и 19200.

**Регистрация по образцу
[`CompositePrinterService`](../../../src/VvCash/Services/Hardware/CompositePrinterService.cs)**,
а не «прочитать настройки один раз при старте»: тот подписан на
`ISettingsService.SettingsChanged` и пересобирает состав. Дисплей делает то же самое, иначе
после настройки порта придётся перезапускать кассу. Порт не задан — служба молча ничего не
делает, и это нормальное состояние кассы без VFD; эту роль берёт на себя переименованный
`NullCustomerDisplayService`.

**Честная граница, и она шире, чем у принтера.** Инициализацию (`ESC @`) и выбор кодовой
страницы (`ESC t n`) понимают практически все VFD. Команды позиционирования курсора у
моделей расходятся сильнее, чем у принтеров. Поэтому реализация консервативная —
инициализация, кодовая страница, затем 40 символов двумя строками по 20, как сейчас.

### Где живут обе кнопки проверки

На экране настроек, в карточке принтеров: «Пробная печать» — своя кнопка у каждой записи
принтера, потому что кодовая страница задаётся на принтер и проверять надо именно её.
«Проверить дисплей» — одна, рядом с настройками VFD. Обе показывают результат там же, через
уже существующий на этом экране баннер `ErrorMessage`/`HasError`, а не молчат.

Пробная печать печатает образец, по которому видно ровно то, что проверяется: строку
кириллицы, строку латиницы, цифры и разделитель — не «Hello world».

## Проблема 4 — дробное количество на чеке обмена

[`ReturnReceiptLine`](../../../src/VvCash/Models/ReturnReceiptLine.cs) объявляет
`int Quantity`, и выданная сторона обмена приводит туда `decimal`
(`ExchangeViewModel`: `new ReturnReceiptLine(l.Product.Name, (int)l.Quantity, ...)`), из-за
чего 1.4 кг печатается как «x1».

Поле становится `decimal`. Возвращаемая сторона при этом честно целая: `ReturnLineVm.ReturnQty`
— `int`, серверный `ReturnLineRequest.Quantity` тоже, так что `decimal` покрывает оба случая
без выдумывания дробных возвратов.

Форматирование выносится в один маленький статический хелпер: в
[`CartItem`](../../../src/VvCash/Models/CartItem.cs) уже есть `QuantityDisplay` (`0.###`) и
`QuantityInUnitDisplay` (`0.######`), и третья копия той же логики на чеке — прямой путь к
расхождению.

## Проблема 10 — гонка при пересборке списка принтеров

`CompositePrinterService.InitializePrinters()` заменяет `_printers` по `SettingsChanged`,
пока печать может идти.

**Почему перенесено из батча D.** Кнопка пробной печати делает связку «поменял настройку →
сразу печатаю» **обычным** сценарием, а не редким. Этот батч сам повышает достижимость
гонки, значит и чинить её должен он, а не следующий.

**Как чинится.** Без блокировки: `InitializePrinters` собирает новый список и присваивает
его одним движением (присваивание ссылки атомарно), а каждый метод печати первым делом
берёт локальную копию ссылки и дальше работает только с ней. Печать, начатая до смены
настроек, доводится до конца на прежнем составе; следующая берёт новый. Блокировка здесь
была бы хуже: методы печати `await`-ят сетевой и последовательный ввод-вывод, и держать на
нём мьютекс — значит подвесить экран настроек на время печати.

Новые ключи заводятся сразу в пяти локалях `ru/en/tg/uz/kk`: подписи полей кодовой
страницы, порта и скорости VFD, кнопки пробной печати и проверки дисплея, и сообщения об их
результате. Недостающий ключ [`I18nService`](../../../src/VvCash/Services/I18nService.cs)
рендерит на экран как `[Ключ]`, то есть промах виден кассиру, а не в логе.

Терминология сверяется с тем, что уже есть в каждом файле, — в батче A два перевода
разошлись с соседними строками того же экрана именно потому, что этого не сделали.

## Тестирование

**Покрывается юнит-тестами:**

| Что | Как |
|---|---|
| Каталог кодовых страниц | чистая функция, зеркало `PhoneFormat`/`RenderingSelector` |
| Байты чека в выбранной кодировке | сравнение с `Encoding.GetEncoding(866).GetBytes(...)` |
| Префикс `ESC t n` присутствует и несёт нужный селектор | новый тест — сегодня команды нет вообще |
| `QuantityDisplay` на чеке | 1.4 → «1.4», 2.0 → «2» |
| Регистрация провайдера кодировок | тест, падающий с `NotSupportedException` без неё |

**Три существующих теста придётся переписать.** `EscPosUnitTest`, `EscPosReturnTest` и
`EscPosExchangeTest` декодируют результат через `Encoding.UTF8.GetString`. Это не «поправить
строчку»: сегодня они проходят **именно потому**, что мы шлём UTF-8, то есть подтверждают
баг. Переписать их на выбранную кодировку — часть исправления, а не побочная уборка.

**Не покрывается принципиально:** интероп с winspool, последовательный порт, и главное —
понял ли принтер байты. Ни один тест не отличит правильную кодовую страницу от неправильной:
обе дают валидные байты.

## Приёмка

Батч A заканчивался ручным проходом, который можно было выполнить. Этот **закончить в
репозитории нельзя** — принтера нет ни у заказчика, ни у исполнителя.

1. Здесь: зелёная сборка, зелёные тесты, и код, который перестал рапортовать успех там, где
   его не было.
2. На точке с принтером: пробная печать → видно кириллицу, кодовая страница угадана; видно
   мусор — выбрать другую из списка; не подошла ни одна — правка каталога и релиз.
3. Находки #3 и #4 считаются закрытыми только после шага 2.

Кнопка пробной печати — не удобство, а единственный способ сделать эту проверку выполнимой
без участия разработчика.

## Вне скоупа

- Инвентаризация парка принтеров на бэкенде. Помогла бы выбрать кодовую страницу
  централизованно, но это второй репозиторий и отдельная задача.
- Автоопределение модели по имени в спулере. Имя задаёт драйвер и его правят руками, а
  незнакомая модель всё равно упала бы в дефолт — пробная печать решает ту же задачу честнее.
- Остальные находки ревью — батчи C и D.
